# 单阶段内容 Schema

每个项目的 6 个阶段均遵循此结构。方案是主叙事，决策融入演进过程。

## 阶段结构

```yaml
stage:
  name: enum [立项与业务价值, 需求分析, 数据准备, 方案设计, 测试验证, 部署与运营]
  probing_intensity: enum [极高, 高, 中]

  # ── 方案本体 ──
  solution:
    final_design:
      description: string
        # 这个阶段你做出了什么东西——系统/框架/体系/方案
        # 描述它怎么运作、关键组件是什么
      deliverables:
        - string
        # 交付物清单（文档/系统/方案/报告等）

    evolution_trail: list | null
      # 演进脉络（有迭代故事时展开，无则留空）
      - version: string         # 如"V1""初版""调整后"
        approach: string        # 当时的方案
        problem_found: string   # 发现了什么问题
        trigger: string         # 什么触发了迭代
      # 最后一条的 approach 即为 final_design
      # 决策自然融入演进过程，不单独抽出来列

  # ── 落地参数 ──
  execution_params:
    - param_name: string        # 如"标注周期""PoC耗时""测试轮次"
      value: string             # 如"3周""2轮""8000条"
      unit: string              # 如"周""轮""条"
    calibration_source: string  # 校准依据（团队规模/项目周期/公司体量）
    reasonable_path: string     # 所选路径（自研/外包标注/开源+校验等）及理由
    # 约束：数字必须互相咬合
    # 示例：8000条 ÷ 3人 ÷ 15天 ≈ 178条/人/天（法律文本合理范围100-200条）

  # ── 追问预埋 ──
  probing_prep:
    - type: enum [方案类, 决策类, 落地类, 反思类]
      question: string          # 面试官可能问的问题
      answer_points: string     # 回答要点（第一人称，引用具体项目细节）
    # 数量要求：
    #   追问强度"极高"的阶段：≥4组（每类至少1组）
    #   追问强度"高"的阶段：≥3组
    #   追问强度"中"的阶段：≥2组

  # ── 低置信度标记 ──
  low_confidence_markers:
    - field: string             # 哪个字段不确定
      reason: string            # 为什么不确定
      needs_user_input: string  # 需要用户提供什么信息
```

## 6个阶段的"本体"形态

| 阶段 | 方案本体是什么 | 追问强度 |
|------|--------------|---------|
| 立项与业务价值 | **立项论证**：市场判断、ROI模型、说服路径 | 极高 |
| 需求分析 | **需求框架**：用户画像、需求分层、优先级矩阵、原型 | 高 |
| 数据准备 | **数据体系**：数据来源、标注方案、质量管控流程 | 中 |
| 方案设计 | **系统方案**：架构、技术栈、组件设计 | 极高 |
| 测试验证 | **评测体系**：指标定义、测试集、评分标准、Bad case归因 | 高 |
| 部署与运营 | **上线方案**：灰度策略、监控体系、迭代机制 | 中 |

## 追问类型说明

| 类型 | 面试官意图 | 答案应引用 |
|------|-----------|-----------|
| 方案类 | "你们做了什么？怎么运作的？" | 方案本体的 final_design |
| 决策类 | "为什么这么做？考虑过别的吗？" | 演进脉络中的转折点 |
| 落地类 | "花了多久？几轮？多少数据？" | 落地参数 |
| 反思类 | "如果重新做会怎么改？" | 演进过程中后来意识到的更优解 |
