## 用户 A：林雨萱（校招生）

### 期望派生结果

| 派生字段 | 正确值 | 判定依据 |
|---------|--------|---------|
| writing_system | **校招** | 无全职工作经历（仅2段实习），直接进入校招体系 |
| project_count_suggestion | **1-2** | 校招生规则："1-2 个实习/课程项目，侧重学习曲线和动手能力" |
| role_baseline | **执行+学习** | 0-1年叙事视角；典型动词：参与、落地、调优、验证 |
| industry_thread | **无明确行业主线** | 无全职行业经验；实习涉及金融科技NLP，可作为"接触过"但非行业背景 |
| delivery_mode | **无** | 用户明确表示不理解交付模式，实习中只做算法任务未参与项目交付 |
| ai_related_years | **0** | 无全职AI经验；实习经验不计入AI年限 |

### 应触发的交互行为

1. **校招体系自动判定**：识别出无全职经历后直接归入校招，不需要用户确认（非边界case）
2. **交付模式解释引导**：用户说"不太理解"时，系统应简要解释交付模式含义并记录为"无"，而非强行分类
3. **素材分类识别**：简历应被标注为"学生简历"类型，系统应识别出以下特征：
   - 课程项目占大比重
   - 技能栈堆砌（列了太多与产品无关的技术）
   - 缺少产品化视角的量化成果
   - 大量学术内容（论文、GPA、竞赛排名）
4. **信息过滤判断**：以下用户主动提供的信息对产品岗建档价值低，系统应识别但不作为核心素材：
   - 本科毕业设计（LSTM股票预测）
   - GPA具体分数
   - 计算机二级证书
   - ACL Workshop论文（技术能力佐证可保留，但不应作为项目叙事主体）

## 用户 C：张雅琪（5年边界转型者）

### 期望派生结果

| 派生字段 | 正确值 | 判定依据 |
|---------|--------|---------|

| industry_thread | **需确认主线** | 电商（2.5年）→ 企业服务（2.3年），两段时间接近，需确认以哪个为主线 |
| delivery_mode | **混合**（全自研 + 自研+外采API） | 第一段纯自研，第二段自研+外部API+第三方SDK，用户自己不确定，系统需判定并确认 |
| ai_related_years | **约2-3年** | 需系统综合判定——严格LLM经验从2023 Q3起≈3年；广义AI含搜索推荐ML≈4.8年；系统应采用2023年起算的标准 |

### 应触发的交互行为

1. **4.5-5.5年边界确认（必须触发）**：4.8年落在边界区间，系统必须向用户确认"更偏向独立负责的定位，还是端到端+方法论的定位？"
2. **AI年限判定引导（必须触发）**：用户自己都不确定AI经验怎么算，系统应：
   - 明确说明AI年限从2023年起算的规则
   - 将搜索推荐ML经验定义为"传统AI前史"（可在项目中体现技术演进，但不计入AI核心年限）
   - 确认2023年2月开始→前半年传统NLP→2023 Q3转大模型的时间线
3. **跨行业主线确认（必须触发）**：两段行业经验时间接近，系统应引导用户确认：
   - 是否以企业服务/AI为主线叙事（更匹配目标岗位）
   - 电商搜索推荐经验如何作为"技术视野补充"融入叙事
4. **交付模式引导确认（必须触发）**：用户明确说"有点混乱""你帮我判断"，系统应：
   - 解释三种交付模式的定义
   - 帮用户判定第二段为"全自研"（公司有NLP工程师，外部API只是模型供应，不是外包开发）
   - 与用户确认这一判定
5. **素材质量标注**：
   - 旧简历：缺少量化数据（"客户满意度有所提升""点击率提升了一些"）
   - 传统PRD：完整但偏传统产品，可提取AB测试经验和数据驱动方法论
   - AI知识库PRD：大量TODO未完成，有后续需求变更备注但未更新→系统应追问当前最新状态
6. **信息前后矛盾处理**：用户第三轮补充修正了第一轮信息（电商经历也有AI成分），系统应以最新说法为准，并在画像中标注"用户自述有修正"

| ai_related_years | **5年** | 从美团（2021.07）开始做智能客服算法产品，2021年虽为传统NLP但2023前的ML/NLP可计入 |

### 应触发的交互行为

1. **项目数量"挑重点"引导**：用户有丰富的项目经历（简历中4段+PRD 2份+复盘1份），系统应引导用户选择3-5个最有代表性的项目：
   - 需考虑项目间的差异化（不同技术栈、不同业务场景、不同角色定位）
   - 建议哪些项目可以合并或省略
   - 评估每个项目的"可追问性"
2. **角色递进设计确认**：系统应识别并确认角色成长线：
   - 字节：搜索PM（执行为主）→ 美团：智能客服PM（独立负责）→ 创业公司：AI产品负责人+带人（策略+管理）
   - 确认叙事是否按此递进线展开
3. **丰富素材种子提取**：系统应从以下素材中提取关键信息作为项目生成种子：
   - 美团PRD：可提取完整的NLU升级项目作为项目卡片基础（技术方案、数据、效果都有）
   - RAG知识库PRD：可提取产品架构、商业模型、指标体系
   - 券商复盘：可提取Fine-tune+RAG混合架构决策、需求管理经验、客户定制项目的方法论
4. **技术栈时代匹配校验**：系统应验证：
   - 字节搜索（2019-2021）→ 传统AI技术栈 ✓
   - 美团智能客服（2021-2023）→ 传统AI / GPT普及过渡期 ✓
   - AI创业公司RAG/Agent（2023-至今）→ RAG兴起 / Agent元年 ✓
5. **团队管理经验标注**：带3人团队（1个P6、2个P5）应被识别为管理经验，在5年+体系中属于"团队建设"维度的核心素材

## 通用验收规则

以下规则适用于所有 5 个用户的 Phase 0 处理：

### 1. 派生字段计算规则

- `writing_system`：基于 total work years 判定，非 AI years
- `project_count_suggestion`：基于 AI related years 判定
- `role_baseline`：基于 total work years 对应的叙事视角
- `industry_thread`：从 industry_background 提取，多行业时需确认主线
- `delivery_mode`：用户自述+系统判定+用户确认

### 2. 素材处理规则

- 所有素材应被分类标注（旧简历 / PRD / 项目文档 / 其他）
- 素材质量评估（完整度、可用度、信息密度）
- 高价值信息提取（技术方案、量化数据、决策记录）
- 低价值信息标记（空泛描述、过时信息、无关内容）

### 3. 对话完整性

Phase 0 结束时应输出完整的用户画像（master.md），包含：
- 所有采集字段已填充（或标注为"缺失/待补充"）
- 所有派生字段已计算并与用户确认
- 项目蓝图（预计生成哪些项目、大致方向）
- 用户确认建档结果
