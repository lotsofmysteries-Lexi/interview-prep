# Phase 1: 场景选择（每项目×1）

## 目标

为单个项目选择具体业务场景，确保该场景既有通用性（面试官能理解），又有差异化（不烂大街）。

---

## 交互逻辑

```
if 用户有意向场景:
    → 场景评估 + 差异化建议
elif 用户已有素材中包含项目信息:
    → 素材提取 + 场景确认 + 差异化增强
else:
    → 系统推荐 3 个场景 + 比选
```

---

## 路径 A：用户有意向场景

### 评估维度

系统对用户提出的场景做"面试竞争力评估"：

| 维度 | 评估问题 | 红线 |
|------|---------|------|
| 场景热度 | 这个场景在面试中有多常见？ | 过于烂大街 → 必须有差异化角度 |
| 行业契合 | 与用户的行业背景是否匹配？ | 完全无关 → 需要用户提供转行叙事 |
| 技术深度 | 是否足以展示 AI PM 能力？ | 纯 API 包装 → 深度不够，建议加深 |
| 可追问性 | 面试官能有意义地追问多少轮？ | 追不下去 3 轮 → 项目太浅 |
| 与已有项目差异 | 和已生成的项目是否重复？ | 场景和技术栈都雷同 → 换方向 |

### 输出格式

```
场景评估：[用户提出的场景名]

✅ 行业契合：与你的 XX 行业背景高度匹配
⚠️ 场景热度：知识库问答是高频场景，建议加入差异化角度
✅ 技术深度：RAG + 混合文档处理有足够技术含量
✅ 可追问性：数据处理、检索策略、效果评估都有深入追问空间

差异化建议：
  你的行业是建筑工程，可以在以下方向做差异化——
  1. 处理工程规范中的表格、图纸、公式混合内容（不是纯文本）
  2. 多版本规范的时效性管理（旧版→新版，哪个适用？）
  3. 跨标准的条款冲突检测

建议采用方向 1，它与你的行业经验最匹配，且技术深度足够。
确认这个场景方向吗？
```

## 数字化成熟度预判（所有路径共用）

在进入场景选择的任何路径之前，先判断该项目所在公司的数字化成熟度档位（L1-L4，见 `calibration-rules.md` §5.4）。

**判断依据**（优先级从高到低）：
1. 用户简历/素材中关于公司和项目的描述
2. 公司行业和规模（传统制造业中型公司 ≈ L1-L2，互联网大厂 ≈ L3-L4）
3. 用户画像中的行业背景

**判断结果影响**：
- 场景评估的"AI 落地策略"：低档位公司的项目，AI 能力嵌入数据治理本身（如用 LLM 做非结构化抽取、跨系统字段对齐），而非直接做上层应用；但项目叙事仍须体现 AI 深度
- 推荐场景时的技术栈约束：与公司实际数字化能力匹配
- 传递给 Phase 2 骨架生成：作为"为什么要做"和"为什么用 AI"的论证基础

如果信息不足以判断，在场景确认前向用户追问：**"这个项目所在的公司，当时有什么样的数字化基础？（有业务系统吗？数据是打通的还是各管各的？之前碰过 AI 吗？）"**

## 路径 B：从已有素材提取

如果用户在 Phase 0 上传了包含项目信息的素材：

1. **提取场景要素**：从素材中识别业务场景、技术栈、角色、成果
2. **生成场景确认**：将提取的信息呈现给用户确认
3. **差异化增强**：评估提取场景的竞争力，提出增强建议

```
从你上传的 [素材名] 中，我识别到一个可以深化的项目：

原始描述：[素材中的描述摘要]

提取的场景要素：
  业务场景：合同审查自动化
  技术栈：NLP + 规则引擎
  你的角色：产品经理
  提到的成果：审查效率提升

差异化增强建议：
  原始描述偏通用，建议在以下方向深化——
  1. 加入 LLM 辅助判断环节（时间线匹配 2024 年的技术趋势）
  2. 聚焦建筑施工合同的特有条款（变更签证、质保金、工期延误）
  3. 加入条款风险分级体系（不只是提取，还要评级）

要在这个方向继续深化吗？还是重新选择场景？
```

## 路径 C：系统推荐

### 推荐逻辑

基于以下输入生成 3 个候选场景：

| 输入 | 作用 |
|------|------|
| 行业背景 | 场景必须与行业相关或有合理迁移 |
| 当前项目序号的技术时代 | 技术栈必须匹配时间线（calibration-rules.md） |
| 已有项目列表 | 避免场景重复，确保差异化 |
| 目标岗位 JD（如有） | 优先匹配 JD 中的能力要求 |

### 输出格式

```
为项目 [N]（时间段 YYYY.MM-YYYY.MM，技术时代 [XX]）推荐以下 3 个场景：

场景 A：[场景名]
  一句话描述：[描述]
  适合理由：[为什么适合这个用户]
  差异化角度：[怎么讲得不一样]
  风险提示：[可能的弱点]

场景 B：[场景名]
  一句话描述：[描述]
  适合理由：[为什么适合这个用户]
  差异化角度：[怎么讲得不一样]
  风险提示：[可能的弱点]

场景 C：[场景名]
  一句话描述：[描述]
  适合理由：[为什么适合这个用户]
  差异化角度：[怎么讲得不一样]
  风险提示：[可能的弱点]

我推荐场景 [X]，因为 [推荐理由]。你选哪个？也可以在某个场景的基础上调整。
```

### 推荐质量规则

- 3 个场景必须彼此有差异（不同业务问题，不同技术侧重）
- 每个场景必须有具体的行业/技术约束，不能是"通用知识库问答"
- 推荐理由必须引用用户画像中的具体信息
- 风险提示要诚实，不要全是优点

---

## 场景确认后

用户选定场景后，存储场景信息，进入 Phase 2（一页纸骨架生成）。

场景信息作为 Phase 2 的输入：
- 场景名称 + 一句话定位
- 差异化角度
- 技术时代约束
- 行业契合说明

---

## 跨项目场景管控

| 规则 | 说明 |
|------|------|
| 场景不重复 | 两个项目不能是同一个业务场景的变体 |
| 技术栈有差异 | 每个项目的核心技术栈应不同（RAG vs Agent vs 传统 ML） |
| 行业一致或有叙事 | 同行业优先；跨行业需用户提供转行故事 |
| 复杂度递进 | 整体上体现从简单到复杂的趋势（非硬约束） |
