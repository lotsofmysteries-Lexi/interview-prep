# Phase 3: 6 阶段全量生成（每项目×1）

## 目标

基于一页纸骨架，**推演**这个项目在实际落地过程中每个阶段的方案、演进、问题和解决方式。产出遵循 `schemas/stage-content.md` 的结构：方案本体（最终方案 + 演进脉络）+ 落地参数 + 追问预埋。

---

## 核心生成理念

### 推演，不是扩写

```
❌ 扩写：骨架说"用了RAG" → 展开写RAG的通用原理和步骤
✅ 推演：骨架说"建筑工程规范文档问答 + RAG" →
   推演：工程规范文档有什么特殊性？（表格+图纸+公式混合）
   推演：这种混合文档用通用切片策略效果如何？（差）
   推演：产品经理会怎么推动解决？（定义文档预处理流程 → 分类型切片 → 评测迭代）
   推演：中间会遇到什么问题？（图纸OCR效果差 → 降级为元数据索引）
```

### 生成锚点

| 锚点 | 说明 |
|------|------|
| 业务场景 | 所有内容必须具体到这个场景，禁止通用化 |
| 技术栈 | 技术选型必须匹配骨架中的技术栈和时间线 |
| 团队规模 | 工作量、分工必须与团队构成匹配 |
| 交付模式 | 叙事视角必须反映实际的执行分工 |
| 公司体量 | 数据量、决策链、审批流程与公司规模匹配 |
| 跨阶段追问 | 按 `references/cross-cutting-probing.md` 的规则，在各阶段追问预埋中覆盖岗位差异化、年限差异化、非技术高价值维度 |

## 6 阶段生成指南

### 阶段 1：立项与业务价值（追问强度：极高）

**方案本体 = 立项论证**

需要推演的内容：
- 市场判断：这个行业/场景为什么现在适合用 AI？（引用行业数据）
- ROI 模型：投入多少、预期产出多少、回收周期多久（数字要可验证）
- 说服路径：老板/客户关心什么？你怎么包装这个项目？汇报了几轮？
- 行业竞品：竞品怎么做的？你的差异化在哪？

**演进脉络参考**（如有迭代故事）：
- 第一次汇报被打回（理由）→ 调整 ROI 测算方式 → 第二次通过

**落地参数**：
- 调研周期、竞品分析数量、汇报轮次、用户调研人数
- 数字校准：参见 `calibration-rules.md` 5.2 节

**交付模式差异**：
- 全自研：内部立项评审
- 部分外包/服务商：立项 + 供应商技术选型评审

**追问预埋（≥4组，每类至少1组）**：
- 方案类："你的立项论证包含哪些部分？"
- 决策类："为什么选这个时间点做？不早不晚？"
- 落地类："调研了多少用户？竞品分析了几个？"
- 反思类："如果重新做立项，你会改什么？"

---

### 阶段 2：需求分析（追问强度：高）

**方案本体 = 需求框架**

需要推演的内容：
- 用户画像：谁是核心用户？使用频次？典型工作流是什么？
- 需求分层：功能需求 / 非功能需求 / AI 特有需求（准确率、延迟、可解释性）
- 优先级矩阵：哪些需求先做？为什么？
- 交互原型：核心交互流程是什么？AI 能力怎么嵌入用户工作流？
- 需求评审：内部评审 + 用户确认的过程

**演进脉络参考**：
- 第一版需求范围过大 → 砍掉 XX 功能（理由）→ 聚焦核心流程

**落地参数**：
- 调研用户数、需求条目数、评审轮次、原型迭代版本数

**追问预埋（≥3组）**：
- 方案类："需求怎么分层的？优先级怎么排？"
- 决策类："砍了哪些需求？为什么？"
- 落地类："调研了多少用户？原型迭代了几版？"

---

### 阶段 3：数据准备（追问强度：中）

**方案本体 = 数据体系**

需要推演的内容：
- 数据来源：业务数据从哪来？什么格式？什么质量？
- 标注方案：标注规范谁定？标注类别怎么设计？如何处理歧义样本？
- 质量管控：交叉校验、一致性检查、淘汰机制
- 数据增强（如有）：数据不够怎么办？

**演进脉络参考**：
- 初版标注规范发现一致性低 → 重新定义边界 case → 培训标注员 → 一致性达标

**落地参数**（关键——数字必须互相咬合）：
- 数据总量、标注人员数、标注周期
- 一致性指标（Kappa 值）、清洗淘汰率
- 校验公式：`数据量 ÷ 人数 ÷ 天数 ≈ 合理日产能`

**合理路径选择**：
- 自有业务数据 / 外包标注（标准内部定）/ 开源+人工校验 / 半自动标注 / 服务商协助采集

**追问预埋（≥2组）**：
- 落地类："数据从哪来？标注花了多久？多少人？"
- 决策类："标注标准谁定的？歧义样本怎么处理？"

---

### 阶段 4：方案设计（追问强度：极高）

**方案本体 = 系统方案**

需要推演的内容：
- AI 路径评估：为什么选这条技术路线？对比了什么替代方案？
- PoC 验证：PoC 怎么做的？效果怎么样？
- 架构设计：系统架构（**先讲一个请求的完整旅程，再讲模块**）、Agent 编排逻辑（节点/边/状态/条件路由）、兜底与降级链路
- 关键技术决策：按下方"技术判断力深度清单"逐项推演，每项需有"选了什么→为什么→替代方案为什么不选"
- 关键组件设计细节：对核心组件逐个拆解（如结构化输出 Schema 的字段级定义、检索索引构建、Prompt 模板结构、缓存 key 设计），面试被追问"具体怎么做的"时直接用

### 技术判断力深度清单（Stage 4 深度底线）

以下维度是 AI PM 面试时被深挖的高频考点。Stage 4 的 full-card **必须至少覆盖 4 项**，每项需有"设计决策 + 为什么这么选 + 替代方案为什么不选"的三段论。覆盖不足则深度不达标，不能进入 Phase 4。

| 维度 | 要推演什么 | 典型追问 |
|------|-----------|---------|
| 流程编排/状态机 | Agent 之间怎么协作？节点和边怎么定义？状态怎么流转？失败怎么兜底？ | "两个 Agent 出错了怎么办？" |
| 结构化输出 Schema | 核心实体的字段级定义？校验规则？枚举/类型约束？校验失败怎么处理？ | "输出格式怎么保证的？" |
| Prompt 治理 | 多少版？怎么版本管理？怎么确保质量（绑定评测分数）？迭代节奏？ | "Prompt 改了这么多版怎么管的？" |
| 阈值/置信度校准 | 关键阈值怎么定的？用什么数据？扫曲线还是拍脑袋？ | "0.85 这个阈值怎么来的？" |
| 缓存/成本工程 | 缓存什么？key 怎么设计？失效策略？成本拆解可推导？ | "成本降了 48% 怎么算的？" |
| 部署与降级 | 模型怎么部署？并发/超时？降级链路？监控埋点？ | "线上挂了怎么办？" |
| 检索策略 | 索引怎么建？单路还是多路？重排怎么做？为什么这个组合？ | "检索不准怎么优化的？" |
| 模型选型对比 | 选了什么？对比了什么？有实验数据吗？为什么不 fine-tune？ | "为什么用这个模型不用那个？" |

**覆盖规则**：
- 自研项目：至少覆盖 5 项（含流程编排、Prompt 治理、成本工程）
- 服务商合作项目：至少覆盖 4 项（含阈值校准、检索策略）——技术路线怎么评审供应商方案
- 参与执行项目：至少覆盖 3 项——即使参与，也要讲清"我知道技术为什么这么选"

**演进脉络（本阶段几乎一定有迭代故事）**：
- V1 方案 → PoC 效果不理想（哪个指标差？差多少？）→ 分析原因 → V2 调整 → 效果提升

**替代方案要求**：
- 替代方案必须是**真正有人会选的**（"为什么不 fine-tune"是好问题）
- 取舍理由必须扎根于**项目具体约束**（"训练数据只有8000条，fine-tune效果不稳定"比"成本高"有说服力）

**落地参数**：
- PoC 周期、对比方案数、模型评估轮次、Prompt 迭代版本数

**追问预埋（≥4组，每类至少1组）**：
- 方案类："架构怎么设计的？核心模块有哪些？"
- 决策类："为什么选 RAG 不选 fine-tune？试过什么替代方案？"
- 落地类："PoC 做了多久？对比了几个方案？"
- 反思类："现在回头看，架构设计你会改什么？"

---

### 阶段 5：测试验证（追问强度：高）

**方案本体 = 评测体系**

需要推演的内容：
- 评估指标定义：用什么指标衡量？指标定义是什么？
- 评测数据集：怎么构建？覆盖哪些场景？规模多大？
- 评分标准：什么算"好"？阈值怎么定？
- Bad Case 归因：典型的失败模式有哪些？怎么分类？
- UAT 验收：业务方怎么参与测试？验收标准是什么？

**演进脉络参考**：
- 第一轮评测发现 XX 类场景准确率低 → 归因为 XX → 针对性优化 → 第二轮提升

**落地参数**：
- 测试用例数、评测轮次、Bad Case 归类分布、UAT 周期

**追问预埋（≥3组）**：
- 方案类："评估指标怎么定的？什么算上线标准？"
- 决策类："Bad Case 怎么归因的？最难解决的一类是什么？"
- 落地类："测了几轮？每轮改了什么？最终准确率多少？"

---

### 阶段 6：部署与运营（追问强度：中）

**方案本体 = 上线方案**

需要推演的内容：
- 灰度策略：分几步放量？每步的标准是什么？
- 监控体系：上线后监控什么指标？报警阈值？
- 用户培训/推广：怎么让用户接受和使用？
- 持续迭代：上线后发现的问题怎么处理？版本节奏？
- 效果复盘：实际效果 vs 预期目标

**演进脉络参考**：
- 灰度阶段发现 XX 问题 → 暂停放量 → 修复 → 继续

**落地参数**：
- 灰度比例和周期、迭代版本数、用户反馈处理量

**追问预埋（≥2组）**：
- 方案类："上线后效果怎样？和预期比呢？"
- 反思类："如果重新做这个项目，你会改什么？"

## 生成节奏

### 逐阶段生成 + 用户确认

```
对于每个项目：
  for 阶段 in [立项, 需求, 数据, 方案, 测试, 部署]:
    生成该阶段内容
    展示给用户
    用户确认或修改
    if 有低置信度标记:
      区分两档后提示用户补充信息：
        · 数字级 —— 骨架方向成立，只是数值待替换
        · 骨架级 —— 方向本身是推演的，不符则整个项目重做（须提到核对清单第 1 位）
```

> 骨架级风险的判定与写法见 `references/source-boundary.md`；
> full-card 开头须保留一行信源声明，指向 `skeleton.md` 的「信源分界」段。

### 展示格式

每个阶段生成后，按以下格式展示：

```
══════════════════════════════════════
[项目名] — 阶段 N：[阶段名]
══════════════════════════════════════

▎方案本体

[最终方案描述]

交付物：
  - [交付物1]
  - [交付物2]

▎演进脉络

  V1：[初版方案]
    → 问题：[发现了什么]
    → 触发：[什么促使调整]
  V2：[调整后方案]
    → 即最终方案

▎落地参数

  [参数1]：[值]
  [参数2]：[值]
  校准路径：[选择了什么路径，为什么]

▎追问预埋

  [方案类] Q: [问题]
           A: [回答要点]
  [决策类] Q: [问题]
           A: [回答要点]
  ...

▎低置信度标记

  ⚠️ [字段]：[不确定的原因]
     需要你提供：[需要什么信息]
──────────────────────────────────────
```

## 质量检查点

每个阶段生成后，系统内部检查：

| 检查项 | 标准 |
|--------|------|
| 场景具体性 | 内容是否具体到这个业务场景？有没有通用化描述？ |
| 技术一致性 | 技术决策是否与骨架中的技术栈一致？ |
| 数字咬合 | 落地参数之间是否互相一致？能否交叉验证？ |
| 追问覆盖 | 追问预埋数量是否满足追问强度要求？4类是否覆盖？ |
| 角色匹配 | 叙事视角是否与年限→叙事视角表一致？ |
| 交付模式 | 执行分工描述是否与用户的交付模式匹配？ |
| 演进真实感 | 演进脉络是否体现"不是一步到位"的工程真实感？ |
| 技术深度 | Stage 4 是否覆盖技术判断力深度清单中的最低数量？每项是否有"决策+理由+替代"三段论？ |
| **信源一致** | full-card 开头是否声明了信源状况、并指向 skeleton.md 的「信源分界」段？各阶段的「低置信度标记」是否区分了**数字级**（改数字即可）与**骨架级**（方向错则整个重做）？ |

## Phase 3 完成条件

| 条件 | 说明 |
|------|------|
| 6 阶段全部生成 | 每个阶段都有方案本体、落地参数、追问预埋 |
| 用户逐阶段确认 | 每个阶段用户确认或修改后确认 |
| 低置信度标记已处理 | 用户补充了所有标记的信息，或确认系统推测可用 |
| 数字通过咬合检查 | 落地参数之间无矛盾 |

完成后，进入 Phase 4（入库 + 准备度评估）。
