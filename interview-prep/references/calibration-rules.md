# 校准规则

所有项目生成环节共享的校准规则集。下游 skill 也可引用。

---

## 1. 年限 → 项目数量

| AI 相关年限 | 建议项目数 | 说明 |
|------------|----------|------|
| <1年 | 1-2 | 1 个深入项目 + 1 个参与项目 |
| 1-2年 | 2-3 | 可覆盖 2 个技术栈迭代 |
| 3-4年 | 3-4 | 体现完整的 AI 产品经历 |
| 5年+ | 3-5（挑重点） | 不必全列，选最有代表性的 |

**补充规则**：
- AI 相关年限从 2023 年起算（大模型技术大规模普及）
- 2023 年之前的传统 ML/NLP 项目可计入，但需在场景中体现传统技术向大模型的演进
- 校招生（无全职经历）：1-2 个实习/课程项目，侧重学习曲线和动手能力

---

## 2. 年限 → 叙事视角

| 年限 | 叙事重心 | 典型动词 | 角色描述示例 |
|------|---------|---------|------------|
| 0-1年 | 执行+学习 | 参与、落地、调优、验证 | "AI 产品经理（参与XX项目，协助产品设计与需求跟进）" |
| 2-3年 | 独立负责 | 负责、设计、推动、优化 | "AI 产品经理（独立负责XX产品线，向产品总监汇报）" |
| 4-5年 | 端到端+方法论 | 主导、搭建、定义、沉淀 | "高级产品经理（端到端负责AI产品矩阵，带1-2名初级PM）" |
| 5年+ | 策略+团队+规模化 | 牵头、体系化、规模化、决策 | "产品负责人（牵头AI产品线规划，管理3人产品团队）" |

**边界处理**：
- 4.5-5.5年是模糊区间，需向用户确认偏向哪个定位
- 角色跨项目应体现成长趋势，但不必每个项目都升一级
- 大方向递进即可，两个项目同级别（但场景不同）是允许的

## 3. 时间线 → 技术栈匹配

| 时间段 | 技术时代 | 主流 AI 技术 | 典型产品形态 |
|--------|---------|-------------|-------------|
| 2023 前 | 传统 AI | 传统 ML、NLP、推荐系统、CV | 算法产品、规则引擎、推荐系统 |
| 2023 H1 | GPT 普及 | GPT API 接入、基础 prompt engineering | ChatGPT 套壳、对话产品、内容生成 |
| 2023 H2 | RAG 兴起 | RAG、向量数据库、fine-tuning | 企业知识库、垂直问答、文档理解 |
| 2024 | Agent 元年 | Agent、工具调用（function calling）、多模态 | AI Workflow、智能助手、RPA+LLM |
| 2025 | 复杂 Agent | 复杂 Agent 编排、多 Agent 协作、AI 原生应用 | AI Infra、多 Agent 系统、AI+行业深度融合 |
| 2026 | 前沿探索 | （当前前沿技术） | 按实际趋势判断 |

**使用规则**：
- 项目的 `time_period` 必须与对应技术时代匹配
- 不是硬绑定：2024年做 RAG 项目也合理（RAG 仍在广泛使用），但 2023 H1 做 Agent 不合理
- 技术栈跨项目应体现成长趋势，但不死守线性递进
- 先做 Agent 再补 RAG 基建是合理叙事（"做了 Agent 发现检索不行，回过头补 RAG 基础设施"）

## 4. 交付模式 → 叙事视角

**核心原则**：交付模式只影响"谁执行"，不影响"谁懂技术"。

无论哪种模式，用户（数字化/数智化团队成员）都深度参与方案设计，对技术细节非常了解。**面试时绝不能出现"这个交给供应商了我不清楚"**——用户必须能讲清每个技术决策的理由。

| 交付模式 | 执行分工 | 叙事侧重 | 追问侧重 |
|---------|---------|---------|---------|
| 全自研 | 内部团队完成全部开发 | 方案设计 + 动手实现 + 效果调优 | 技术细节、实现取舍 |
| 部分外包 | 方案自主设计，开发/标注等执行环节找外包 | 方案设计 + 供应商技术对接 + 质量管控 | 方案为什么这么定？怎么管控外包质量？ |
| 服务商合作 | 内部出方案，服务商协助实施 | 方案主导权 + 技术对标 + 验收标准 | 技术路线怎么定的？服务商方案怎么评审？ |

**6 阶段在不同交付模式下的叙事差异**：

| 阶段 | 全自研 | 部分外包 / 服务商合作 |
|------|--------|---------------------|
| 立项与业务价值 | 内部立项评审 | 立项 + 供应商技术选型评审 |
| 需求分析 | 直接做用户访谈 | 用户访谈自己做，需求文档基线化后与供应商对齐 |
| 数据准备 | 内部团队标注 | 标准内部定，执行可外包标注/服务商协助采集 |
| 方案设计 | 自己做选型 + PoC | 自己出方案，对齐供应商技术实现，主导评审 |
| 测试验证 | 内部测试闭环 | 自己定验收标准 + 评测体系，管控供应商交付质量 |
| 部署与运营 | 自主上线运维 | 灰度策略自己定，部署执行可由供应商配合 |

## 5. 落地参数校准（How much）

### 5.1 校准原则

每个阶段的数字必须**互相咬合**，构成可验证的内部一致性：

```
示例——数据准备阶段：
  标注数据量：8000条
  标注人员：3人
  标注周期：15天
  → 178条/人/天（法律文本的合理范围：100-200条/天）✅

反例：
  标注数据量：50000条
  标注人员：2人
  标注周期：5天
  → 5000条/人/天（不合理）❌
```

### 5.2 常见参数的合理范围

#### 调研/立项阶段

| 参数 | 小团队（<10人） | 中团队（10-50人） | 大团队（>50人） |
|------|---------------|-----------------|---------------|
| 调研周期 | 1-2周 | 2-4周 | 4-8周 |
| 竞品分析 | 3-5个 | 5-10个 | 10+个 |
| 立项汇报轮次 | 1-2轮 | 2-3轮 | 3-5轮 |
| 用户调研人数 | 5-10人 | 10-30人 | 30+人 |

#### 数据准备阶段

| 参数 | 合理范围 | 说明 |
|------|---------|------|
| 文本标注速度 | 100-300条/人/天 | 取决于文本长度和标注复杂度 |
| 图片标注速度 | 200-500张/人/天 | 简单分类；复杂标框降至50-100 |
| 标注一致性(Kappa) | ≥0.7 | 低于0.6需重新定义标注规范 |
| 数据清洗淘汰率 | 10-30% | 高于50%说明数据源有问题 |
| 标注人员数 | 2-5人（小项目），5-20人（中大项目） | 含交叉校验人力 |

#### 方案设计/PoC 阶段

| 参数 | 合理范围 | 说明 |
|------|---------|------|
| PoC 周期 | 2-6周 | 含数据准备和效果评估 |
| 对比方案数 | 2-4个 | 至少有1个基线对比 |
| 模型评估轮次 | 2-5轮 | 每轮有明确调优方向 |
| Prompt 迭代版本 | 5-20版 | RAG/Agent 类项目 |

#### 测试验证阶段

| 参数 | 合理范围 | 说明 |
|------|---------|------|
| 测试用例数 | 200-2000条 | 与业务场景复杂度正相关 |
| 评测轮次 | 2-4轮 | 每轮修复后复测 |
| Bad Case 归因 | 按类型占比排 | 如"实体识别错误40%、逻辑推理错误30%..." |
| UAT 周期 | 1-3周 | 含业务方确认 |

#### 部署运营阶段

| 参数 | 合理范围 | 说明 |
|------|---------|------|
| 灰度比例 | 5%→20%→50%→100% | 分3-4步放量 |
| 灰度→全量周期 | 2-6周 | 取决于用户量和风险等级 |
| 上线后迭代版本 | 2-5个 | 3个月内的小版本 |

### 5.3 公司体量校准

| 公司体量 | AI 团队规模 | 数据量级 | 决策链 |
|---------|-----------|---------|-------|
| 创业/小型（<100人） | 1-3人 | 千级-万级 | 1-2层，快速 |
| 中型（100-1000人） | 3-10人 | 万级-十万级 | 2-3层 |
| 大型（>1000人） | 10-30人 | 十万级-百万级 | 3-5层，流程重 |
| 集团/央国企 | 按项目组建 | 百万级+ | 多层审批，周期长 |

**规模一致性校验**：
- 小公司不会有10人 AI 团队
- 大公司不会只有1个产品经理管所有 AI 项目
- 团队规模 × 项目周期 = 合理的总工作量
- 数据量级与公司业务规模匹配

## 6. 差异化策略

**核心公式**：通用场景 + 行业/技术约束条件 = 差异化项目

### 差异化示例

| 通用场景（烂大街） | 差异化方向 | 差异化后 |
|------------------|-----------|---------|
| 客服机器人 | B端 SaaS + 多租户 | 多租户客服 Agent，处理跨租户知识隔离 |
| 知识库问答 | 建筑行业 + 混合文档 | 工程规范文档问答，处理表格/图纸/公式混合内容 |
| 合同审查 | 施工行业 + 变更签证 | 施工合同条款风险分级，含工程特有的变更签证条款 |
| 智能客服 | 金融 + 合规约束 | 金融咨询问答，需满足投顾合规要求和风险提示 |
| 文档生成 | 医疗 + 结构化病历 | 医疗病历自动结构化，处理多科室术语差异 |

### 差异化评估维度

| 维度 | 问题 | 红线 |
|------|------|------|
| 场景热度 | 这个场景面试中烂大街吗？ | 如果太热门→必须有差异化角度 |
| 行业契合 | 与用户行业背景是否匹配？ | 跨行业项目需要用户自己提供转行叙事 |
| 技术深度 | 是否足以展示 AI PM 能力？ | 纯 API 调用包装→深度不够 |
| 可追问性 | 面试官能追问多少轮？ | 追不下去3轮→项目太浅 |

## 7. 写作哲学

### 7.1 项目描述原则

- **不写痛点**：不说"以前多痛苦"，直接写"我做了什么、做出了什么"
- **写行动不写感受**：删掉"深入理解了""充分调研了"，换成具体动作
- **写营收不写省钱**：优先说"创造了XX价值""提升了XX效率"，其次才是"节省了XX成本"
- **具体不抽象**：不说"搭建了RAG系统"，说"基于XX向量库 + XX切片策略搭建了XX领域的RAG检索系统，支持XX类文档的混合检索"
- **数字要可验证**：每个数字都要能用项目内的其他数字推算出来

### 7.2 禁止清单

| 禁止 | 替代 |
|------|------|
| "深入调研了行业痛点" | "调研了15名XX角色用户，提取了3类核心需求" |
| "成功搭建了XX系统" | "搭建了XX系统，上线后XX指标从A提升到B" |
| "优化了用户体验" | "将XX操作的步骤从5步缩减至2步，用户完成率从60%提升至85%" |
| "积累了丰富经验" | 删掉，用项目事实替代 |
| "具有良好的沟通能力" | 删掉，让项目中的跨部门协调事实来证明 |
| "通用化描述 RAG 流程" | 写具体的切片策略、检索策略、重排序逻辑 |

### 7.3 量化成果书写规范

```
✅ 好的量化：
"条款提取准确率从72%提升至91%（基于200份标注测试集）"
"合同审查周期从平均5天缩短至1天，法务团队腾出约60%精力用于高价值谈判"
"上线3个月处理合同1200+份，人工复核率从100%降至15%（仅低置信度结果需人工）"

❌ 差的量化：
"大幅提升了效率"
"准确率达到90%以上"（没有基线对比）
"节省了大量人力"
```

## 8. 写作体系（年限分层）

### 校招体系

- 项目来源：实习/课程/竞赛/开源贡献
- 叙事重点：学习曲线、动手能力、解决问题的思路
- 忌：装老练，说"我主导了""我带领团队"
- 宜：诚实讲学到了什么、做了哪些尝试、遇到什么困难怎么解决

### 社招 0-5 年体系

- 叙事重点：独立负责能力、技术判断力、项目推动力
- 角色定位：模块级到产品线级的独立负责人
- 忌：过度包装（把参与说成主导）、缺少决策点
- 宜：讲清楚"你做了什么决定""为什么这么选""效果怎样"

### 社招 5 年+体系

- 叙事重点：方法论沉淀、团队建设、业务策略、规模化
- 角色定位：产品线负责人/团队管理者
- 忌：还在讲执行细节（应该讲决策和体系）
- 缺：没有方法论沉淀、没有带人经验
- 宜：讲"搭建了什么体系""建立了什么流程""培养了几个人"
