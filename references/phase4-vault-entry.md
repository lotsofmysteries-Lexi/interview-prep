# Phase 4: 入库 + 准备度评估

## 目标

将 Phase 3 生成的全量内容入库为完整项目档案，自动提取索引信息供下游 skill 使用，并通过两层评估判断项目"面试准备度"。

---

## Step 1: 组装完整档案

将 Phase 3 的 6 个阶段内容 + Phase 2 的骨架，按 `schemas/project-card.md` 组装为完整项目档案：

```yaml
project_card:
  metadata:
    project_id: proj-{NNN}
    skeleton_ref: interview-vault/projects/proj-{NNN}/skeleton.md
    created_at: [当前日期]
    last_modified: [当前日期]
    readiness_score: [待计算]
    readiness_details: [待生成]

  stages:
    stage_1_initiation: [Phase 3 阶段1内容]
    stage_2_requirements: [Phase 3 阶段2内容]
    stage_3_data: [Phase 3 阶段3内容]
    stage_4_design: [Phase 3 阶段4内容]
    stage_5_testing: [Phase 3 阶段5内容]
    stage_6_deployment: [Phase 3 阶段6内容]

  extracted_indices: [Step 2 生成]
```

## Step 2: 自动提取索引

从完整档案中自动提取以下信息：

### 技能标签

```
遍历每个阶段的方案本体和技术栈：
  提及但未深入描述 → proficiency: 能用
  在方案本体中有具体运作描述 → proficiency: 懂原理
  在演进脉络中有取舍讨论 → proficiency: 能讲取舍
```

### 量化指标

```
遍历每个阶段的落地参数和骨架中的预期成果：
  提取 metric_name + value + source_stage
  去重，保留最终值
```

### 能力证据

```
遍历方案本体和演进脉络：
  识别能力标签（技术选型、跨部门协调、项目推动、数据治理等）
  关联具体的证据内容
```

### 追问题库

```
汇集所有阶段的追问预埋：
  按 type（方案/决策/落地/反思）分类
  按 probing_intensity 排序
```

### 关键词

```
全文提取关键词：
  技术栈关键词
  行业关键词
  方法论关键词
  工具/平台关键词
```

如果已有其他项目入库，对新入库项目做增量一致性校验：

按 `schemas/consistency-check.md` 的维度，检查新项目与已入库项目之间的一致性。

## Step 4: 准备度评估（两层）

### 第一层：结构完备性（自动检查）

| 检查项 | 标准 | 权重 |
|--------|------|------|
| 6 阶段覆盖 | 每阶段有方案本体（最终方案 + 交付物） | 20% |
| 量化指标 | ≥3 个量化成果（含业务指标 + AI 指标），通过行业常识校验 | 15% |
| 追问预埋 | 极高追问阶段每个 ≥4 组，高追问 ≥3 组，中追问 ≥2 组 | 20% |
| 落地参数 | 数据准备和测试验证阶段有具体的人天/耗时/轮次/数量 | 15% |
| 演进脉络 | ≥2 个阶段有完整的演进故事（V1→问题→V2） | 15% |
| 角色一致性 | 全阶段叙事视角与年限匹配，无矛盾 | 10% |
| 数字咬合 | 落地参数之间无矛盾，可交叉验证 | 5% |

**评分规则**：
- 每项检查通过 = 满分
- 部分通过 = 按完成比例折算
- 未通过 = 0 分
- 总分 = 各项加权求和（0-100）

### 第二层：叙事自检（系统自追问）

系统扮演面试官，对自己生成的全量档案做 3-5 轮追问测试：

**追问测试流程**：

```
for 追问 in 随机选取的 3-5 个追问预埋:
  提取追问预埋中的 question
  用档案中的内容尝试回答
  检查：
    1. 答案是否自洽？（前后不矛盾）
    2. 答案是否够具体？（不模糊带过）
    3. 能否继续追问 2 层？（追问→再追问→再追问，都有内容可答）
  
  if 发现漏洞:
    标记为待补充
```

**追问测试覆盖**：
- 至少覆盖"极高追问"的 2 个阶段（立项、方案设计）
- 至少包含 1 个跨阶段追问（如"方案设计阶段的选型依据和 PoC 阶段的效果是否一致？"）
- 至少包含 1 个"反思类"追问

### 准备度输出

```
准备度评估：[项目名]
─────────────────────────────────────────

结构完备性：88/100
  ✅ 6阶段覆盖：完整
  ✅ 量化指标：4个（业务2+AI 2），校验通过
  ✅ 追问预埋：极高阶段各4组，高阶段各3组，中阶段各2组
  ⚠️ 落地参数：数据准备阶段缺标注人天参数 → -7分
  ✅ 演进脉络：方案设计+测试验证阶段有完整迭代故事
  ✅ 角色一致性：全阶段一致
  ⚠️ 数字咬合：标注数量与周期的日产能未明确 → -5分

叙事自检：3/5 轮通过
  ✅ 追问1："为什么选RAG不选fine-tune？" → 答案引用了数据量约束，自洽
  ✅ 追问2："上线后效果怎样？" → 答案有具体数据，可继续追问
  ⚠️ 追问3："数据标注花了多久？" → 答案缺人天参数，追问到第2层中断
  ✅ 追问4："架构怎么设计的？" → 答案完整，可追问3层
  ⚠️ 追问5："如果重新做会怎么改？" → 答案偏泛，需更具体的改进点

综合准备度：85%
  主要缺口：
    1. 数据准备阶段的标注人天参数需补充
    2. 反思类追问的回答需更具体
  
  建议：补充以上2项后可达90%+，面试准备充分
─────────────────────────────────────────
```

## Step 5: 用户确认与补充

```
[项目名] 的准备度评估结果如上。

需要你补充的信息：
  1. [缺口1的具体提问]
  2. [缺口2的具体提问]

你也可以选择：
  - 补充信息后重新评估
  - 跳过补充，当前准备度已满足需求
  - 修改已生成的内容
```

用户补充后，重新计算准备度。

---

## Step 6: 入库存储

准备度评估完成后（无论是否达到满分），将完整档案存入 vault：

```
interview-vault/projects/proj-{NNN}/
├── skeleton.md      # Phase 2 已存
├── full-card.md     # 完整档案（本步骤存入）
└── qa-bank.md       # 追问QA库（从 extracted_indices.qa_bank 导出）
```

---

## 面试复盘的回流机制

面试后如果使用了 interview-review skill 进行复盘，可能产生档案补丁：

1. 补丁存储在 `interview-vault/interviews/<公司-日期>/patches/`
2. 系统提示用户逐条确认补丁内容
3. 用户确认后合并回 `full-card.md`
4. 合并后 `last_modified` 更新
5. `readiness_score` 重新计算
