### Q-AT-001：你了解哪些主流大语言模型（国内/海外）？它们的能力优势有什么区别？
- 变体问法: "你用过哪些主流大模型，区别是什么？"、"DeepSeek 和 GPT 比有什么优势，为什么成本更低？"
- tags: [llm-landscape, model-comparison, moe]
- 回答框架:
  1. 按开源/闭源盘点国内外主流模型及各自擅长点（生成/语音/长文本/数学代码/中文/生态），强调结合现实动态
  2. 收敛到自己所在行业：哪些厂商在行业内中标多、有领域增强模型，客户用脚投票
  3. 开源 vs 闭源：开源可私有化部署微调、适合定制与数据敏感场景；闭源 API 稳定、按量付费、适合快速试错
  4. 按任务复杂度匹配参数规模：简单分类用小参数指令模型，多数业务用中等参数，复杂长文档/多模态推理用大参数推理模型
  5. DeepSeek 类低成本原理：MoE 架构按需激活专家、国产算力适配与推理引擎优化、量化蒸馏压缩，中文语料比例高；GPT 生态成熟、英文与复杂推理强
  6. 观点收尾：B 端落地中模型间差异在缩小，数据质量与业务 know-how 才是护城河

### Q-AT-002：谈谈你对指令模型和推理模型的理解
- tags: [reasoning-model, instruction-model, model-selection]
- 回答框架:
  1. 目标差异：推理模型聚焦逻辑链推导（数学/代码/科学计算）；指令模型专注理解执行明确指令（生成/翻译/问答）
  2. 训练范式：推理模型重强化学习优化推理路径；指令模型重 SFT+RLHF 对齐人类偏好
  3. 交互差异：推理模型自主拆解步骤、展示思考链；指令模型需明确步骤、提示词专业度影响大
  4. 产品设计：可设"深度思考"开关按复杂度切换；任务步骤多或需验证过程用推理模型，有明确 SOP 或需快速响应用指令模型
  5. 成本权衡：推理成本远高于指令模型，需在场景中量化价值；趋势是指令模型做理解层+推理模型做执行层的融合
- 融合钩子: full-card 方案细节

### Q-AT-003：谈谈你对大模型的边界有什么看法？
- tags: [ai-boundary, limitation, product-design]
- 回答框架:
  1. 技术边界：事实幻觉、上下文窗口限制、知识时效性差、本质是语言模式预测缺乏因果推理、长对话前后矛盾、无法主动获取外部数据
  2. 产品应用边界：受 prompt 影响大、不适合结构化高频低价值场景、响应延迟；敏感领域需后处理与规则过滤
  3. 伦理合规边界：数据合规、隐私保护、生成内容风险
  4. 擅长面：推理、语义理解、生成、总结，适合知识类与执行类任务
  5. 用项目举例收敛：如生成错误专业建议→加 RAG+答案溯源提升可信度；理解边界才能做出加知识库、启人审、模板化等设计决策

### Q-AT-004：根据你自己的理解讲一下 AI Agent？为什么大家都在专攻 Agent，大模型解决不了么？
- 变体问法: "现在让你去搭一个 Agent，你会怎么搭，有哪些节点？"
- tags: [agent, llm, task-planning]
- 回答框架:
  1. 定义：LLM+观察+思考+行动+记忆；核心技能是 function calling 与 ReAct 推理执行
  2. 为什么需要 Agent：简单任务直接 LLM 即可；复杂任务需拆解规划，避免 prompt 过载；Agent 能解决数据实时更新问题（大模型是存量数据）
  3. 企业落地形态：不是单点工具，而是平台+构建+行业 know-how-workflow 的完整解决方案，打通烟囱系统
  4. 三层结构设计（进阶）：能力层（大脑：LLM/插件）、结构层（神经系统：memory/工具管理/上下文）、行为层（意图-动作/任务分解）
  5. 落地节点：意图识别→任务规划→工具/接口调用→结果校验→回答生成，配数据反馈闭环
- 融合钩子: full-card 方案细节

### Q-AT-005：RAG 知识库是怎么构建的？落地步骤与更新机制是怎样的？
- 变体问法: "你做的问答产品中 RAG 的落地步骤是怎样的，非结构化知识如何加工？"、"十年的老旧数据怎么清洗、怎么提高知识库质量？"、"知识库文档更新、切片过时怎么处理，处理文档还是切片？"
- tags: [rag, knowledge-base, chunking, data-cleaning]
- 回答框架:
  1. 离线流程（构建知识库）：多源异构数据接入 → 数据提取（OCR/文档解析+人工复核）→ 分块 → 向量化 → 入库建索引
  2. 数据提取：明确数据源与格式，去噪、格式统一、去重保证准确性；不可编辑 PDF 走 OCR+解析，人工核对文字与版式
  3. 分块：按内容意图/固定大小/句分隔/递归分隔，按文档类型选策略（手册按目录、FAQ 按问答对），兼顾成本与响应时间
  4. 老旧数据清洗：基础清洗（去重/格式统一）+ 按时效性、查询频率、业务重要性筛选，不一刀切；打状态标签（有效/历史/废弃）
  5. 质量提升：元数据（更新时间/业务分类/重要性）+重排序加权（相似度×时间加权×业务系数×频率系数）+大模型预检人工兜底
  6. 更新机制：版本号+更新时间，增量替换而非全量重建；旧版切片归档不可检索但可审计；高时效内容即时重建索引，低时效批量更新
  7. 价值收尾：知识库限定检索范围、让模型有据可依，降低幻觉
- 融合钩子: full-card 方案细节

### Q-AT-006：你有没有参与过模型选型？具体怎么做的？
- 变体问法: "如何评估小模型是否适合我们的场景？"、"RAG 流程中如何选择合适的 LLM？"、"新模型上线如何抉择，更换模型要做哪些工作、是直接全量上线吗？"、"如何做模型选型？"
- tags: [model-selection, evaluation, migration]
- 回答框架:
  1. "3 看 1 测"：看榜单、看训练数据、看厂商在同场景的落地案例；均只作参考，必须用真实业务数据实测
  2. 1 测试流程：设定标准 → 构建评测集（输入-期望输出对，与业务共创高频问题）→ 高阶模型做阅卷者评分 → 专家审核修正 → 扩大测试覆盖
  3. 按节点选型：工作流不同节点能力要求不同，从要求最高的规划类节点开始测，低要求节点跟进；不同环节（索引/路由/改写/生成）可用不同模型组合
  4. 小模型适配判断：任务复杂度（简单分类 vs 多步推理）、数据量与质量、算力资源约束、实测准召
  5. 换模型决策：先判断是否真解决现有痛点并评估成本；离线评测+在线灰度双验证；准备兼容工作（格式、prompt 重调、QPS/成本预估）；小流量灰度逐步替换，可回滚
  6. 补充非技术因素：成本与计费方式、多模态能力、生态与工具链、厂商服务与客户关系等，按项目优先级权衡
- 融合钩子: full-card 方案细节

### Q-AT-007：你的数据评测集是怎么建的？从哪些维度保证数据的质量？
- 变体问法: "数据评测集构建的具体流程是怎样的，你负责什么？"、"你是否有组织数据评估工作的经历？"
- tags: [evaluation-dataset, annotation, quality]
- 回答框架:
  1. 流程与分工：明确评测目标（PM 主导）→ 制定评测集（协同）→ 构建评估体系（PM 主导）→ 覆盖面审核补充 → 人工打分校准 → 结果转化为产品决策
  2. 数据来源：业务共创高频问答、历史客服/日志数据、线上真实问答、大模型辅助生成
  3. 质量六维：准确性（来源可靠、标注准确、覆盖重要特征）、完整性（缺失值处理、量级充足）、一致性（格式统一、清洗彻底）、多样均衡（多场景覆盖、样本均衡）、时效性（定期更新）、隐私合规（匿名化）
  4. 覆盖设计：单轮/多轮/多意图/query 改写模拟真实问法；高频+长尾+边界场景（模糊、错别字）
  5. 标注管控：标注规范先行、交叉抽检验一致性、说明文档定义"对但没解决"等判定逻辑

### Q-AT-008：你是如何做模型效果评测的，整体流程是怎样的？
- 变体问法: "AI 项目上线后如何评估效果，涉及哪些指标，后续如何优化？"、"怎么判断大模型的优化效果达到了预期？"、"做模型评测时遇到过哪些困难？"、"问答率提升怎么算的？"
- tags: [evaluation, metrics, online-monitoring]
- 回答框架:
  1. 四步流程：确定测试数据集（必过集/高频集/badcase 集）→ 制定评估体系与维度 → 确认评测方式 → 比对输出、产出测评报告
  2. 评估维度：指令遵循度、准确度、相关性、人设风格、安全性、多轮理解、体验；生成类产品另有专属维度
  3. 评测方式：GSB 对比打分、分维度评分制、自动标注（裁判模型）+人工打分结合
  4. 上线后评估三层：用户侧直接反馈（满意度）、线上行为数据（活跃、解决率、留存）、A/B 对比；指标分算法指标（准召/F1/BLEU/ROUGE）、性能指标（响应/首字）、业务指标（满意度、解决率、转人工、业务增长）
  5. 量化口径要能讲清：问答率来自埋点、正确率来自测试集批量测试（正确+合理)/总数
  6. 优化闭环：badcase 分析归类→算法定向优化→持续数据优化与反馈机制；评测困难点在标准制定、数据偏差与业务场景适配
- 融合钩子: full-card 咬合总账

### Q-AT-009：如果只评测 RAG 的召回链路和生成链路效果，你会如何制定量化指标？
- tags: [rag-evaluation, retrieval-metrics, llm-judge]
- 回答框架:
  1. 召回链路优化点：追问澄清、多路混合召回、重排、摘要多层索引
  2. 检索指标：Hit Rate@K、召回率；排序指标：MRR、NDCG、排名损失
  3. 可用 LLM 辅助评分：从相关性、信息完整性、噪声比例三方面打分并给理由
  4. 生成链路优化：prompt 调优/思维链、检索内容合并与迭代生成、模型自评估与反思修正
  5. 生成指标：客观（BLEU/ROUGE、Perplexity）+主观分维度（正确性、相关性、流畅性、忠实度、敏感风险）；人工打分+高阶模型评测交叉

### Q-AT-011：我收集到 badcase 了，也分类了，每个类别的 badcase 咋优化？
- tags: [badcase, optimization-loop, root-cause]
- 回答框架:

### Q-AT-012：如何设计即时用户反馈机制，收集用户对模型生成内容的评分与反馈？
- 变体问法: "收到用户的点踩回复，你们是如何处理的？"
- tags: [feedback-loop, ux, data-collection]
- 回答框架:
  1. 设计原则：用户体验轻量化 + 数据有效性并重
  2. 显式反馈：对话界面轻量评分按钮（点赞/点踩/星级）+文本意见；点踩后追问原因做负反馈细化
  3. 隐式反馈：点击率、停留时长、同问题重复追问等行为数据与显式评分交叉验证
  4. 主动式反馈：低置信度内容主动询问用户是否有帮助；游戏化激励（积分兑换）
  5. 点踩处理闭环：定期抽查线上问答，逐条分析打标归类，制定优化策略与指标，量大时 PM 定义 badcase 标注规范保证标注一致性
- 融合钩子: full-card 方案细节

### Q-AT-013：你的 AI 产品的用户满意度是如何收集的？

### Q-AT-014：你是如何撰写 Prompt 的，有什么技巧和心得？
- 变体问法: "基于需求的提示词如何设计？"、"prompt 中加 few-shots 的优缺点是什么？"、"提示词在哪个环境调试的？"
- tags: [prompt-engineering, few-shot, cot]
- 回答框架:
  1. 原则：任务目标明确具体、给足背景上下文、明确输出格式与约束、可引入多轮互动
  2. 递进优化路径：普通口语 → 结构化提示词 → COT 思维链 → 正向 few-shots → 需避免的错误；结构化可遵循 CRISPE 框架
  3. 实操技巧：给模型设定扮演角色、任务拆小按序执行、限定条件（格式/风格）；用高阶模型帮优化 prompt；推理模型反而要 prompt 更简洁重背景
  4. few-shots 优缺点：快、便宜、直观，适合意图少且稳定的场景与 MVP；缺点是吃上下文 token、扩展性差、未覆盖的易分错、需人工维护
  5. 收尾：prompt 是 AI PM 的需求文档，结合项目给一个 prompt 优化前后的真实案例
- 融合钩子: full-card 方案细节

### Q-AT-015：用户的提问 Query 改写扩写你们是怎么做的？
- 变体问法: "RAG 知识问答，先 query 改写再意图识别，还是先意图识别再 query 改写？"
- tags: [query-rewrite, rag, retrieval]
- 回答框架:
  1. 目的：增加关键词命中与向量贴近度，是 RAG 检索优化的核心手段之一
  2. 方式：大模型+提示词实现改写
  3. 五种策略：相同语义重写、样本提示同义重写、抽象化重写、拆解任务重写、Hyde 假设答案重写
  4. 策略选择：以用户真实数据做 few-shots 让模型自选改写方法
  5. 顺序问题分场景回答：多轮对话先改写再意图（上下文合并后输入更规范）；单轮结构化 query 先意图再改写省调用；混合型 Agent 先意图再改写；也可做两次改写（轻量规则改写→意图识别→LLM 二次改写）
- 融合钩子: full-card 方案细节

### Q-AT-016：你们怎么提升大模型的意图识别能力？
- 变体问法: "意图数量太多无法枚举，如何优化意图识别，还用大模型做么？"、"优化意图识别模型时遇到的最大挑战是什么？"
- tags: [intent-recognition, small-model, fallback]
- 回答框架:
  1. 两种做法融合：LLM+few-shots（效果不足可微调）+ 传统分类模型（语义匹配/Bert）；先关键词快召回再大模型排序确认
  2. 意图分层分类：先粗分类（业务流程/知识问答/情绪反馈）再细分树状结构，分阶段识别优于直接多分类
  3. 意图过多场景用小模型+微调+few-shots 为主（LLM 慢且有幻觉），用大模型生成相似问扩充语料
  4. 无法枚举的部分返回"未知意图"类不强制识别，每日收集人工打标补充训练集形成闭环
  5. 兜底机制：监控置信度，低置信 fallback 给大模型分析，仍失败则引导式兜底话术
  6. 挑战案例收尾：歧义/长尾问题→上下文增强+数据精标+产品侧置信度兜底，量化准确率提升

### Q-AT-017：怎么判断用户意图更改了？是只根据当前这句话还是根据所有上下文？

### Q-AT-020：你们在做 RAG 的过程中遇到过哪些难点和坑？
- 变体问法: "RAG 会产生附加问题，比如大模型说不贴合问答的话，如何解决？"
- tags: [rag-pitfalls, engineering, cost]
- 回答框架:
  1. 文档解析坑：格式复杂异构（表格嵌套/扫描件/旧格式）需定制化；分块大小两难（过小丢上下文、过大引噪声）且人工核对成本高；多模态融合难（图表/图纸需视觉模型）
  2. 效果与成本平衡：多节点调用耗时（大模型调用占比高）；纯向量检索解决不了数值比较与实体关系，需混合检索；向量化+调用成本要算清

  5. 不贴合回答的解法：记忆/知识存储准确性、分块与混合检索优化、query 重写、生成 prompt 优化、后处理兜底、渐进话术降机械感、数据反馈闭环

### Q-AT-021：RAG 可能会失效的原因是什么？用户提问不在知识库内如何解决？

### Q-AT-034：在产品侧，如何定义 AI 能用的标准？

### Q-AT-035：大模型微调和 RAG 各有什么优势？你的决策路径是什么？
- tags: [rag-vs-finetune, decision, cost]
- 回答框架:
  1. 本质区别：RAG 外挂知识不改造模型、降幻觉、知识可即时更新；微调改造模型本身、解决模型能力不足
  2. 适用性：微调适合特定任务性能要求极高的专业场景（资源投入大）；RAG 适合多数企业场景（周期短、成本低、风险可控、知识即时更新）
  3. 效果权重参考：模型本身能力、RAG 应用层、SFT 各占影响比例，RAG 性价比更高
  4. 决策优先级：先 prompt 工程+RAG，效果仍不达标再考虑微调

### Q-AT-036：实际工作中用 prompt 还是微调 SFT 如何判断？
- 变体问法: "微调、prompt 提示词优化都是提升效果的手段，区别是什么？"
- tags: [prompt-vs-sft, decision, stage]
- 回答框架:
  1. 原理区别：微调改参数从底层改变能力、需数据与算力、上限高灵活性低；prompt 不改参数、零成本快速迭代、依赖模型原有能力
  2. 决策维度：产品阶段（验证期用 prompt 快速试错，成熟期追求稳定用 SFT）、数据与算法资源（数据有限用 prompt）、场景复杂度（结构化强上下文逻辑复杂适合 SFT）
  3. 混合策略：SFT 保主干能力，prompt 调风格与格式，兼得效果与灵活性
  4. 项目举例：冷启动无数据时 prompt+few-shot 一周上线 MVP；用户量与需求稳定后用积累的问答数据微调提升专业度；最终 SFT+prompt 模板组合
- 融合钩子: full-card 方案细节

### Q-AT-037：微调的数据质量标准如何制定？微调需要多少数据量、有哪些步骤？
- 变体问法: "作为 AI 产品经理参与微调，你的角色和具体贡献是什么？"、"模型精调都有哪些步骤？"、"好的微调数据训练集有什么标准？"
- tags: [fine-tuning, dataset, sft, lora]
- 回答框架:
  1. 数据量评估：按任务难度（简单分类每类千条级、复杂多轮对话万级以上）、模型规模、微调方式（提示微调最少、LoRA 中等、全参最多）、数据质量（人工精标可数倍减量）四方面估
  2. 好训练集标准"高质量、贴合场景、成体系"：来源真实（从高频真实操作与日志筛选）、表达多样（query 改写扩覆盖变体）、每条人工 review 有标注规范与 reject 原则
  3. 结构化设计：按任务链拆解（意图识别→填槽→接口调用与异常处理），分阶段数据便于分段评估与错误定位；准备正例与边界负例提升鲁棒性
  4. 微调步骤与 PM 角色：明确业务目标 → 构建数据集与标注规范 → 与算法协作选方案（SFT/RLHF/LoRA）→ 评估效果给产品判断 → 线上监控与滚动精调闭环
  5. 评估双轨：离线验证集测准确率/调用成功率/填槽正确性；在线灰度看执行成功率、兜底率、满意度

### Q-AT-038：LoRA 微调、SFT 全参微调、提示词微调分别对应什么场景、数据量和资源？
- tags: [lora, sft, prompt-tuning]
- 回答框架:
  1. 提示词微调：需求变化快精度要求不极端；少量 few-shot 即可；几乎零算力，成本最低但依赖模型原有能力
  2. SFT 全参微调：需彻底改造模型或严格输出风格（行业专用模型）；需大规模高质量标注数据；多卡集群训练，成本最高、周期长，效果最好但灵活性差
  3. LoRA 微调：模型有通用能力需领域增强；中等规模精标数据；只更新适配层参数，单卡可训，成本适中易迭代
  4. 实战选型顺序：快速提升体验用 prompt、行业场景稳定复用用 LoRA、打造专属行业模型才上全参
- 融合钩子: full-card 方案细节

### Q-AT-041：你了解 transformer 架构吗？最核心的是什么？
- 变体问法: "RNN/LSTM 跟 transformer 的区别在哪里？"
- tags: [transformer, attention, architecture]
- 回答框架:
  1. 结构：Encoder 理解输入（BERT 类擅长理解）、Decoder 生成（GPT 类擅长生成）；生成型产品多用 Decoder-only
  2. 最核心是自注意力机制：动态判断词与词的全局关联，不再依赖顺序理解语义，支持并行与大规模预训练
  3. 对比 LSTM：按顺序逐词处理、门控机制部分缓解长距离遗忘但不能并行，长文本信息稀释；transformer 全局关联、并行快、长文本与多轮更稳，但参数大推理成本高
  4. 产品视角收尾：关注推理延迟、长上下文承载、多轮状态维护三件事；端侧受限场景可能回退轻量结构
  5. 延伸了解：MoE 架构是多专家路由的可扩展方向，大参数低推理成本
- 融合钩子: full-card 方案细节

### Q-AT-042：谈谈对模型蒸馏、量化、剪枝的定义和理解
- tags: [distillation, quantization, pruning]
- 回答框架:
  1. 一句话总纲：蒸馏是大带小、量化是压精度、剪枝是减冗余，都为更小更快可部署
  2. 蒸馏：大模型教小模型模仿泛化，关注准确率阈值、是否丢失业务特有能力，适合端侧低延迟
  3. 量化：高精度参数压成低精度减少体积与算力，关注精度损失可接受度与端侧场景
  4. 剪枝：删除不重要参数结构，关注是否影响泛化与关键路径
  5. PM 视角：明确业务约束（运行场景、延迟/内存限制）、协助算法选策略组合、推动压缩前后效果对比指标设计、做资源-效果-体验平衡与上线条件设定
- 融合钩子: full-card 方案细节

### Q-AT-044：你的项目用的什么模型，每天消耗 Token 多少、成本多少？

### Q-AT-048：说说对 Deep Research 和 Deep Thinking 的理解及二者的区别
- tags: [deep-research, reasoning, ai-infra]
- 回答框架:
  1. 定位差异：Deep Research 面向基于真实外部资料的实证型任务（行业调研/竞品报告），流程是多源检索→可信度比对→冲突标注→结构化报告，输出可审查
  2. Deep Think 面向内部推理与方案对比：并行生成多个思路/假设，分析优缺点给建议，焦点在推理路径本身
  3. AI infra 支撑差异：Research 需要强检索系统、可信来源库、工具调用与来源验证；Think 依赖模型自身推理、并行假设与自我修正
  4. 产品结合：先 Think 快速探索思路，方案确定后再 Research 确认证据增强可信度
  5. 风险提示：两者成本高，存在误引来源、数据偏差、耗时过长等风险
