# 面试复盘 4 步 Pipeline

## 输入

- 面试转录文稿（ASR 逐字稿或用户口述复盘）
- 面试时冻结的 vault 档案快照（以面试日期为基准）
- JD 原文（如有，用于面试官立场分析）

---

## Step 1: 面试转录文稿解析

将面试录音的转录文稿解析为结构化的问答对列表。

### 解析规则

1. **说话人识别**：区分面试官和候选人
   - 有明确标注 → 直接使用
   - 无标注 → 根据语义判断（提问方 = 面试官，回答方 = 候选人）

2. **问答拆分**：按面试官每次提问拆分为独立 QA 对
   - 候选人回答中包含多个问题的回答 → 按问题拆开

3. **追问识别**：同一话题连续追问 → 标注追问链和追问深度

4. **意图标注**：每个面试官问题打上意图标签（可多选）

| 意图标签 | 说明 |
|---------|------|
| 自我介绍 | 开场自我介绍 |
| 项目深挖 | 针对具体项目的追问 |
| 技术原理考察 | 对技术原理的追问 |
| 动机与职业规划 | 为什么应聘、职业规划 |
| 行为面/情景面 | "遇到XX情况你怎么处理" |
| 追问与压力测试 | 连续追问、质疑 |
| 开放式问题 | 发散性问题 |
| 闲聊/破冰 | 非正式交流 |
| 候选人反问 | 候选人向面试官提问 |

5. **候选人回答摘要**：每个回答生成 2-3 句摘要，保留关键事实和量化数据

6. **候选人表现初判**：

| 等级 | 说明 |
|------|------|
| 完整 | 有数据支撑，逻辑清晰 |
| 不够深入 | 回答了但缺少关键细节 |
| 未答上来 | 答非所问 |
| 越界 | 说了不该说的（暴露知识盲区、泄露敏感信息） |

### 输出格式

```yaml
qa_pairs:
  - id: Q001
    interviewer_question: string
    intent_tags: [项目深挖, 技术原理考察]
    follow_up_depth: 0          # 0=首问，1=追问，2=再追问
    follow_up_chain: null       # 追问链 ID
    candidate_answer_raw: string
    candidate_answer_summary: string
    performance: enum [完整, 不够深入, 未答上来, 越界]
    confidence: enum [高, 中, 低]  # 说话人识别置信度
```

---

## Step 2: 查漏补缺卡片比对

将每个 QA 对与 vault 档案逐题比对。

### 比对逻辑

对每个面试官问题：

1. **应调用档案识别**：理想情况下，应该调用哪个项目的哪个阶段来回答？
   - 匹配 vault 中的 projects/proj-*/full-card.md
   - 记录匹配到的项目/阶段/字段

2. **实际调用判断**：候选人回答中是否使用了对应内容？
   - 已调用：使用了核心内容（数据、方案、取舍）
   - 未调用：档案中有但没讲出来
   - 部分调用：使用了部分，遗漏关键点

3. **缺口分类**：

| 缺口类型 | 说明 | 后续处理 |
|---------|------|---------|
| 档案缺失 | 应有的内容在 vault 中不存在 | → 生成新内容补丁 |
| 档案未调用 | 内容存在但候选人没讲 | → 标记为"下次记得讲" |
| 档案部分调用 | 讲了但遗漏关键点 | → 标记具体遗漏项 |
| 回答越界 | 候选人说了未准备的内容 | → 评估是否应补充到档案 |

4. **评分**（A/B/C/D）：

| 等级 | 标准 |
|------|------|
| A（优秀） | 完整调用，数据准确，逻辑清晰，追问接住 |
| B（良好） | 基本调用，细节遗漏或追问回答不够深入 |
| C（及格） | 部分调用，或回答较浅，追问未能有效应对 |
| D（不及格） | 未调用，或答非所问 |

评分必须列出 3 条具体依据，引用候选人回答原话或关键缺失点。

---

## Step 3: 面试官立场分析

从面试官提问模式中反推关心点和隐性需求。

### 分析维度

1. **问题聚类**：将所有面试官问题按考察维度聚类
   - 聚类名称（如"RAG 技术深度""项目落地能力"）
   - 包含的问题 ID 列表
   - 聚类强度（strong / medium / weak）

2. **关心点排序**：根据以下信号排序
   - 问题数量（问得多 = 关心）
   - 追问深度（追问深 = 重点考察）
   - 问题位置（靠前 = 重点）
   - 追问后是否满意（继续追问 = 之前没满足）

3. **隐性需求识别**（需 JD 原文）
   - JD 没写但面试官重点考察的需求
   - JD 有但面试官没问的内容

### 输出格式

```
面试官立场分析
─────────────────────────────────────────

关心点排序（从高到低）：
  1. AI 技术选型能力 [strong] — 问了5个相关问题，追问3层
  2. 项目推动与跨部门协调 [strong] — 问了4个问题
  3. 数据治理经验 [medium] — 问了2个问题
  4. 团队管理 [weak] — 只问了1个问题

隐性需求：
  ⚠️ JD 未提但面试官重点考察：AI 工程化能力（模型部署、监控）
  ℹ️ JD 有但面试官未问：行业经验（可能默认你已匹配）
─────────────────────────────────────────
```

## Step 4: 档案补丁生成

根据缺口清单生成可执行的补丁包。

### 补丁类型

| 类型 | 触发条件 | 内容 |
|------|---------|------|
| new_content | 档案缺失 | 新建阶段内容或追问预埋 |
| modify_content | 档案部分调用 | 修改已有内容，补充遗漏 |
| add_probing | 追问未预料 | 为追问预埋补充新的 QA 对 |

### 补丁格式

```yaml
patch:
  id: patch-001
  type: enum [new_content, modify_content, add_probing]
  target:
    project: proj-001
    stage: stage_4_design
    field: probing_prep
  source_questions: [Q003, Q004]  # 暴露此缺口的面试题
  reason: "面试官追问了'为什么不用 fine-tune'，档案中只有结论没有对比分析"
  content:
    before: "选择RAG方案"  # 修改前（modify 类型）
    after: "选择RAG方案，因为训练数据仅8000条，fine-tune效果不稳定；对比实验显示RAG在该数据量下准确率高12%"
  priority: enum [高, 中, 低]
  confidence: enum [高, 中, 低]
```

### 补丁合并流程

1. 展示所有补丁给用户，按优先级降序
2. 用户逐条确认（接受/修改/拒绝）
3. 接受的补丁合并回 `full-card.md`
4. 更新 `last_modified` 和 `readiness_score`
5. 记录合并历史

### 去重规则

- 多个缺口指向同一字段 → 合并为一条补丁
- 补丁内容与现有档案重复 → 标注并跳过
- 同一优先级内按目标阶段排序

## 复盘记录存储

```
interview-vault/interviews/<公司-日期>/
├── transcript.md        # 原始转录
├── qa-pairs.md          # Step 1：结构化 QA 对
├── review.md            # Step 2-3：比对 + 立场分析
└── patches/             # Step 4：补丁
    ├── patch-001.md     # 已确认的补丁
    ├── patch-002.md
    └── merge-log.md     # 合并记录
```

## 多次面试的跨面积累

如果同一公司/岗位有多次面试记录：
- 对比多次面试的关心点变化
- 识别反复出现的追问话题
- 合并建议到公司/岗位画像中
