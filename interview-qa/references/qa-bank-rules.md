# QA 交互演练规则

> v2.0：QA 是**交互优化环节**，不是落盘产物。题目来自 qa-db 题库层，事实来自 vault 事实层，现场融合、逐题确认。

## 两层来源

```
题库层：interview-qa/references/qa-db/（通用题，跨 skill 单一事实源）
  ├── index.md                # 总索引（qa-db-tools.py index 生成，勿手编）
  ├── 01-project-experience.md / 02-methodology.md / 03-ai-technical.md
  ├── 04-nontechnical.md      / 05-presale-delivery.md
  └── CHANGELOG.md            # 版本记录（运营维护）

事实层：interview-vault/
  ├── profile/master.md       # 骨架一览 / 软肋清单 / 用户画像
  └── projects/proj-*/full-card.md   # 咬合总账 / 方案细节 / 追问预埋（项目专属 QA 唯一事实源）
```

## 演练流程

### Step 1: 命中

- 读目标项目 full-card 的主题 tags（技术栈、行业、方法论关键词）
- 对照 `qa-db/index.md` 圈定相关题（预期 25-40 题/项目）；按类优先：与项目强相关的 03 类 → 01/02 类 → 04/05 类
- 可用 `scripts/qa-db-tools.py dedup --query "<主题>"` 辅助检索

### Step 2: 融合（框架 × 事实）

每道命中题按其"融合钩子"注入事实：

| 融合钩子 | 注入来源 |
|---------|---------|
| full-card 咬合总账 | 成本/收益/指标类问题的具体数字 |
| full-card 方案细节 | 架构/实现类问题的具体决策 |
| master 骨架一览 | 项目概况/业务价值类问题 |
| master 软肋清单 | 失败/不足/争议类问题的防守口径 |
| master 用户画像 | 动机/规划类问题 |

**铁律**：答案中的数字必须能在咬合总账中回溯推导；回溯不了的数字不许出现在答案里。

### Step 3: 逐题交互

```
每题一轮：
  出题（题干 + 变体问法可切换）
  → 用户作答（或"看参考"）
  → 对照参考框架给反馈（漏了什么框架要点 / 哪些事实可用而未用 / 软肋防守是否到位）
  → 下一题
```

用户可随时说"跳过这类""来几道非技术的""专攻 RAG"调整选题。

### Step 4: 与追问预埋去重

- full-card `extracted_indices.qa_bank`（追问预埋）是**项目专属 QA 的唯一事实源**，不重复演练
- 命中题与追问预埋考点重叠时，只讲题库框架带来的**增量视角**，或跳过

### Step 5: 留存（仅用户要求）

写入 `interviews/qa-sessions/{日期}-{主题}.md`：本次演练的题号清单 + 用户薄弱点记录。不进 `projects/`，不生成 qa-bank.md。

## 答案质量规则

| 维度 | 要求 |
|------|------|
| 第一人称 | 用"我"讲述，不用"该项目""团队" |
| 引用具体细节 | 引用项目中的具体数据、方案名、技术选择 |
| 可追问 | 答案本身可以被继续追问至少 1-2 层 |
| 不矛盾 | 同一项目不同阶段的答案之间不矛盾 |
| 不通用 | 不能用在别的项目上也成立的泛泛回答 |
| **信源一致** | 覆盖 🔴 零字全推演内容时必须提示 `source: fabricated`，用户知情后选择讲法 |

## 高频通用追问（交互中补充）

以下 5 条引用该项目演进脉络与 metrics 现场生成，注意各项目**讲法边界**（如个人工具项目价值不得折算成金额）：

| 问题 | 回答来源 |
|------|---------|
| "这个项目最大的挑战是什么？" | 从演进脉络中选最有张力的转折点 |
| "你在项目中最大的贡献是什么？" | 从方案本体中选最核心的设计决策 |
| "如果重新做会怎么改？" | 从反思类追问中选最有深度的 |
| "项目的量化成果？" | 从 extracted_indices.metrics 中选 |
| "团队怎么协作的？" | 从团队构成 + 交付模式推演 |
