# 岗位动态拆解分析框架

## 概述

本文档定义了岗位JD结构化拆解的方法论。核心设计：**先解码JD信号，再识别岗位类型，最后映射到对应的专属分析框架**，而非用一套固定模板套所有岗位。

## JD信号解码方法论

### 设计思想

JD不是简单的"要求清单"，而是公司AI应用规划的**逆向投影**。招聘方在JD中写下的每一条要求，本质上是"我们已经规划了但尚未具备的能力"的外显。尤其对于AI应用岗位，JD信号解码的价值远超关键词匹配——它能帮你理解公司正在建什么、处于什么阶段、需要什么类型的人。

### JD三模式分类

#### A型·模糊型

**定义**：JD对候选人能力要求笼统、岗位边界不清，无法从JD推断出入职后的具体工作内容。

**识别信号**：
- 职责描述使用泛化词汇（"负责AI产品规划""推动AI落地"）但无具体场景
- 任职要求与岗位职责不对应（要求全栈但岗位只写了一个方向）
- 薪资范围窄且偏低（说明公司对这个岗位的投入预期有限）
- JD篇幅短、信息密度低
- 同一岗位长期反复招聘（说明招不到或招到了留不住）

**反推逻辑**：
- A型JD = 公司自己也不确定要什么。可能是：
  - 部门刚组建，业务方向未定，先招人再说
  - 钓鱼式招聘——挂出来看看市场上有什么人
  - 真实需求和JD描述不匹配（内部已有明确需求但HR不会写）

**分析策略**：保守推断，重点识别风险。面试核心是反向引导——通过提问弄清真实工作范围。

**典型案例**：
> 某公司招"AI产品经理"，JD只写"负责AI产品的规划和落地"，要求"熟悉大模型技术，有产品思维"。无法判断是做B端还是C端，是0到1还是1到10。

#### B型·清晰型

**定义**：JD明确描述了入职后的工作场景、产出物和KPI方向，候选人与岗位的映射关系可验证。

**识别信号**：
- 职责描述到具体功能/场景级别（"负责XX模块的AI能力设计"）
- 任职要求可映射到具体工作产出（要求RAG经验→产品中有知识库功能）
- KPI方向可从JD推断
- 薪资范围与要求匹配
- 团队规模、汇报关系有描述

**反推逻辑**：
- B型JD = 公司已有明确规划和成熟需求。岗位是执行层而非探索层。
- JD中每个具体要求都对应一个已规划的产品方向或技术路线
- 从要求的技能栈可以反推公司AI架构的技术选型

**分析策略**：确定性高，重点展示对应场景的执行能力。面试核心是证明"我能做你们需要的事"。

**典型案例**：
> 某公司招"RAG知识库产品经理"，JD明确写了"负责企业知识库的RAG检索优化，提升检索准确率至95%+"，要求"有RAG系统设计经验，了解向量数据库选型"。

#### C型·扩池型

**定义**：JD要求范围明显宽于岗位层级，跨领域组合要求，薪资带宽大——公司在用一个JD覆盖多个可能的方向，以扩大人才池。

**识别信号**：
- 经验年限与能力要求不匹配（1-3年经验却要求"领域建模"能力）
- 同时要求多个方向的深度经验（B端+C端、技术+业务、策略+运营）
- 薪资带宽>30%（如2.2-4万），暗示跨级别招聘
- JD中包含"之一"或"至少满足N项"的表述
- 要求跨界复合能力而非单一专精

**反推逻辑**：
- C型JD = 公司有远大规划但不想限定太死。可能是：
  - 产品方向还在探索，需要能适应多种方向的人才
  - 多个相关方向需要同一个PM来串联
  - 公司在"人才池扩容"——先招到优秀的人，再根据能力定岗
  - 用一个JD同时招聘P6和P7，面试定级

**分析策略**：机会与风险并存。核心是展示跨领域能力的同时锚定一个主攻方向。面试中主动提出"我理解你们在同时做X和Y，我的优势在X，但Y我也能覆盖"——这比泛泛说"我都可以"更有说服力。

**典型案例**：
> 蚂蚁阿福招"AI应用产品经理（健康档案/健康生活方向）"，1-3年经验要求，但同时要求领域建模、C端产品经验、AI架构理解。薪资2.2-4万（P6-P7双级别）。JD用一个岗位覆盖了健康档案和健康生活两个方向，且能力要求远超1-3年经验的常规水平。

### JD信号→公司AI规划反推表

以下为常见JD信号与对应的公司AI规划反推。此表为分析时的参考框架，具体分析需结合JD原文和公司背景综合判断。

| JD信号 | 反推的公司AI规划 | 可信度 | 适用条件 |
|:------|:-------------|:------|:--------|
| 要求"AI+行业"复合经验 | 公司AI走行业垂直路线，不做通用工具 | 高 | AI应用岗 |
| 要求"从0到1"经验 | AI应用处于起步阶段 | 高 | 非大厂成熟业务线 |
| 要求C端+B端双经验 | 产品可能是C端获客+B端变现，或C端是B端入口 | 中高 | 平台型产品 |
| 要求"领域建模"而非"原型设计" | 需要架构型PM，不是传统功能PM | 高 | AI产品岗 |
| 要求"规则引擎/知识图谱" | AI架构是混合推理（规则+LLM） | 高 | 技术/产品岗 |
| 要求"多Agent"经验 | 产品架构已规划多Agent并行 | 中 | AI产品/开发岗 |
| 要求特定行业经验但放宽年限 | 行业壁垒高，AI无法替代行业知识，但人才稀缺 | 高 | 垂直行业AI岗 |
| 要求"Prompt Engineering" | 公司AI应用以LLM为核心，不是传统ML | 高 | AI运营/产品岗 |
| 要求"数据标注经验" | 公司AI还处于冷启动阶段，数据基建未完成 | 高 | AI算法/运营岗 |
| 要求"跨部门协作"且篇幅占比高 | AI团队是赋能型定位，不是独立产品线 | 中高 | 所有AI岗 |
| JD中"AI"出现频率高但场景描述少 | 公司AI战略高调但落地模糊 | 中 | A型JD常见 |
| 要求"开源模型部署"经验 | 公司走自研/私有化路线，不依赖API | 高 | AI工程岗 |
| 同时要求"用户体验"和"技术理解" | 产品处于"AI能力产品化"阶段，不是纯技术验证 | 高 | AI PM岗 |

### 面试运用指南

JD信号解码的核心面试价值：**在面试中展示"我不只是看到了JD的字面要求，我理解你们在建什么"**。

**运用方式**：

1. **产品理解环节**：基于C型JD反推，主动说出你对产品架构的判断
   - "我注意到JD同时覆盖了X和Y方向，我的理解是你们正在构建以X为底座、Y为用户触点的闭环产品"
   - 效果：比"我觉得你们产品很好"更能展示战略思维

2. **自我介绍环节**：将反推结果作为你"为什么适合"的论据
   - "你们的JD对领域建模能力的要求让我判断，你们需要的不是一个画原型的PM，而是一个能把业务知识结构化为AI系统架构的人，这正是我的核心能力"
   - 效果：精准对位，比泛泛说"我有X年产品经验"更有说服力

3. **提问环节**：基于反推结果设计验证性问题
   - 基于C型JD的扩池推断："我理解这个岗位可能涉及X和Y两个方向，目前团队在这两个方向的资源分配和优先级是怎样的？"
   - 效果：展示你已经在思考入职后的工作方式

4. **风险验证环节**：基于A型JD的模糊信号，确认真实工作范围
   - "JD中提到的AI产品方向比较宽泛，能否具体说说入职后前三个月的主要工作目标？"
   - 效果：避免入职后发现与预期不符

## 岗位类型识别规则

从以下信号中综合判断JD所属的岗位类型：

**识别优先级（从高到低）**：
1. JD标题中的明确岗位名称
2. JD开头的"岗位职责"概述中的关键词密度
3. "任职要求"中的技能栈特征
4. 团队/部门描述

| 编号 | 类型 | 标识关键词（示例） | 典型角色偏向光谱 |

## 通用分析维度（所有岗位共享）

无论哪种岗位类型，都需覆盖以下四大分析板块：

### 板块A — 公司信息检索与情报收集

**信息源矩阵（6维度5-10分钟速查）**：

| 信息源 | 获取方式 | 关键情报价值 | 优先级 |
|--------|----------|--------------|--------|
| **官网** | 公司官网、招聘页面、产品/解决方案介绍 | 主营业务、产品矩阵、技术方向、企业文化 | ⭐⭐⭐⭐⭐ |
| **新闻** | 科技媒体、行业报道、融资新闻 | 发展阶段、战略重点、近期动态、市场声量 | ⭐⭐⭐⭐⭐ |
| **管理层讲话** | 财报电话会、公开演讲、内部信 | 战略优先级、组织调整信号、资源投入方向 | ⭐⭐⭐⭐ |
| **研报** | 券商研报、行业分析报告 | 财务健康度、竞争格局、行业地位、增长预期 | ⭐⭐⭐⭐ |
| **现有员工** | 脉脉、看准网、小红书、知乎 | 团队氛围、工作强度、领导风格、真实薪资 | ⭐⭐⭐⭐⭐ |
| **近期招投标** | 政府采购网、招标平台、公司中标公告 | 业务扩张方向、客户类型、项目规模、现金流 | ⭐⭐⭐ |

**情报整合输出**：

- **公司画像**：规模、阶段（初创/成长/成熟）、融资情况、主营业务、主要客户群体
- **行业生态位**：在产业链中的位置、竞争对手、护城河
- **技术方向**：公司的AI技术应用方向（对内提效 vs 对外产品）
- **组织动态**：近期架构调整、团队扩张/收缩信号、战略优先级变化
- **录用偏好推测**：从JD措辞、公司发展阶段、近期招聘动态中综合推断
- **风险提示**：基于员工反馈和招投标异常信号识别的潜在风险点

## 各岗位类型的专属分析框架

### T01 算法工程师

**能力栈分层**：

| 层级 | 内容 |
|------|------|
| 硬技能 | 深度学习框架熟练度、论文复现能力、数学基础（线性代数/概率论/优化）、编程语言（Python/C++）、分布式训练经验 |
| 行业Know-how | 特定领域的数据特性（CV/NLP/推荐/时序等）、数据标注策略、模型选型的业务权衡 |
| 软技能 | 文献阅读与跟进节奏、技术方案表达能力、与工程团队的协作效率 |

**角色偏向光谱**：学术研究 ←———————————→ 工程落地
- 左侧特征：发论文、跟SOTA、探索新方法
- 右侧特征：模型压缩、部署优化、上线指标

**KPI可能维度**：模型精度指标（准确率/F1等）、推理性能（延迟/QPS）、项目交付周期、论文产出（若偏研究）

**Know-how可迁移性**：
- 高可迁移：深度学习通用方法论、框架使用能力、建模思维
- 中等可迁移：特定领域的建模技巧（跨领域需适应期）
- 低可迁移：特定业务的领域知识

### T02 AI产品经理

**能力栈分层**：

| 层级 | 内容 |
|------|------|
| 硬技能 | AI技术边界认知（能做什么不能做什么）、产品设计与原型工具、数据分析能力、竞品分析方法 |
| 行业Know-how | 所在行业的业务流程与痛点、AI在该行业的成熟应用模式、客户决策链路 |
| 软技能 | 跨角色翻译（把技术讲给业务听，把业务需求翻译给技术）、优先级判断力、不确定性下的决策能力 |

**角色偏向光谱**：用户洞察 ←———————————→ 技术理解
- 左侧特征：深挖用户场景、用户体验设计、GTM策略
- 右侧特征：技术可行性评估、AI方案设计、技术选型判断

**KPI可能维度**：产品关键指标（DAU/转化率/留存等）、AI功能采纳率/渗透率、产品上线节奏、客户反馈满意度

**Know-how可迁移性**：
- 高可迁移：AI PM方法论（需求评估→方案定义→效果衡量）、跨角色协作能力
- 中等可迁移：行业know-how（跨行业有折损但底层逻辑相通）
- 低可迁移：特定产品的用户洞察和领域知识

### T03 解决方案架构师

**能力栈分层**：

| 层级 | 内容 |
|------|------|
| 硬技能 | AI技术全栈了解（不需要精通但需要广度）、系统架构设计、云平台熟悉度（AWS/阿里云等）、POC搭建能力 |
| 行业Know-how | 目标行业的IT现状与痛点、采购决策流程、竞品方案的优劣、典型项目的实施路径 |
| 软技能 | 方案演讲与演示能力、客户需求引导能力、内部资源协调能力、抗压能力（售前周期长且不确定） |

**角色偏向光谱**：方案设计 ←———————————→ 客户交付
- 左侧特征：写方案文档、做技术选型、画架构图
- 右侧特征：现场POC演示、客户沟通谈判、项目交接

**KPI可能维度**：方案胜率/中标率、POC转化率、支撑的合同金额（ACV）、客户反馈评分

**Know-how可迁移性**：
- 高可迁移：方案设计方法论、客户沟通技巧、技术广度和快速学习能力
- 中等可迁移：特定行业的解决方案经验（同赛道内高度可迁移）
- 低可迁移：特定客户关系和区域市场知识

### T04 AI运营 / AI应用运营

**能力栈分层**：

| 层级 | 内容 |
|------|------|
| 硬技能 | Prompt Engineering、AI工具使用熟练度、数据分析（Excel/SQL/Tableau）、A/B测试方法、内容创作能力 |
| 行业Know-how | 所运营产品/服务的用户特征、AI生成内容的质量标准、平台规则与算法机制、运营增长方法论 |
| 软技能 | 敏感度（捕捉热点和用户情绪变化）、执行力（高频迭代）、跨部门协同（尤其与技术团队对接AI能力） |

**角色偏向光谱**：内容/创意运营 ←———————————→ 数据/增长运营
- 左侧特征：文案/创意、用户社区运营、品牌调性把控
- 右侧特征：漏斗分析、转化率优化、实验驱动决策

**KPI可能维度**：AI功能使用率/活跃度、内容生产效率提升比、用户留存/增长指标、人效提升比例

**Know-how可迁移性**：
- 高可迁移：AI工具使用方法论、数据驱动运营思维、A/B测试能力
- 中等可迁移：增长方法论（跨产品通用）

## KPI推断通用方法论

当JD中没有明确的KPI描述时，根据以下线索推断：

**直接线索**（JD中提到的）：直接作为KPI候选
**间接线索**（从岗位类型反推）：使用上述各岗位类型的KPI维度
**隐藏线索**（从公司阶段反推）：
- 初创公司 → 更看重产出速度和多功能性（一人多角）
- 成长期公司 → 更看重规模化和效率指标
- 成熟公司 → 更看重合规、流程、稳定性

## Know-how可迁移性评估矩阵

每次分析结束时，对当前岗位的know-how做一次可迁移性打分（1-5分），帮助用户理解"这个岗位干几年之后能带走什么"：

| 分值 | 含义 | 说明 |
|------|------|------|
| 5 | 高度通用，跨行业无缝衔接 | 如：Python编程、项目管理方法论、数据分析思维 |
| 4 | 较高通用，跨行业小幅适应 | 如：某类AI应用开发经验、MLOps方法论 |
| 3 | 中等通用，同行业内可迁移 | 如：特定领域的AI解决方案经验、垂直行业的客户资源 |
| 2 | 较低通用，窄赛道内有价值 | 如：特定公司的业务know-how、特定产品线经验 |
| 1 | 高度绑定，离开即失效 | 如：特定公司的内部流程、纯内部工具链的使用经验 |

输出格式建议：将岗位的核心能力项逐一列出，每项附一个可迁移性分数。
