### 素材2：PRD——美团智能客服升级项目（超级详细）

```
=====================================
PRD：美团智能客服系统 NLU 模型升级
=====================================

文档信息
────────────────────────
版本：v2.4（终版）
产品经理：李沐阳
最后更新：2022.11.20
状态：已上线 & 效果验证完成
关联文档：技术方案文档 TDD-2022-AI-015、数据埋点方案 DA-2022-038

一、需求背景

1.1 业务现状

美团智能客服系统承载外卖、酒旅、到店三大业务线的用户咨询，日均对话量约160万次（高峰期可达220万次）。当前系统基于规则引擎+关键词匹配实现自动应答：
- 规则库维护成本高：当前共维护3200+条规则，每月新增/修改约150条
- 自动解决率停滞：近6个月自动解决率维持在45%左右，且新增规则的边际收益递减
- 多业务适配困难：外卖/酒旅/到店的咨询模式差异大，共用规则库导致误匹配率约8%
- 人力成本压力：未被自动解决的55%对话全部转人工，客服团队约1200人，年人力成本约1.8亿

1.2 竞品对标

| 维度 | 美团（当前） | 京东 | 淘宝 |
|------|------------|------|------|
| 技术方案 | 规则引擎 | BERT分类 | 自研NLU |
| 自动解决率 | 45% | 65% | 72% |
| 意图识别准确率 | N/A（无模型） | 88% | 91% |
| 多轮对话 | 不支持 | 3轮 | 5轮 |

1.3 核心问题定义

将智能客服系统的对话理解能力从规则引擎升级为NLU模型，目标：
- 自动解决率从45%提升至70%+
- 降低规则维护成本（减少70%规则数量）
- 支持多轮对话（至少5轮有效对话）

二、目标用户

2.1 用户画像

| 用户类型 | 描述 | 核心需求 | 日均量级 |
|---------|------|---------|---------|
| 外卖用户 | 下单/配送/退款咨询 | 快速解决，时效敏感 | 约100万次 |
| 酒旅用户 | 预订/退改/发票咨询 | 流程复杂，需多轮确认 | 约35万次 |
| 到店用户 | 团购/优惠券/门店咨询 | 场景多样，长尾需求多 | 约25万次 |

2.2 用户旅程分析

典型外卖咨询流程：
用户进入客服 → 描述问题 → 系统识别意图 → 确认关键信息（订单号、问题类型）→ 给出解决方案 → 用户确认 → 关闭会话

当前痛点在第3步：规则引擎对自然语言理解能力差，用户表述稍有不同就无法识别。

例：
- "骑手还没到"→ 规则匹配 ✅
- "外卖都半小时了还没送来"→ 规则未匹配 ❌（但本质是同一意图）
- "你们骑手是不是跑路了"→ 规则未匹配 ❌

三、需求详述

3.1 意图识别模块

3.1.1 意图分类体系

采用两级意图分类：一级意图 × 二级意图

外卖业务线：
| 一级意图 | 二级意图 | 历史占比 |
|---------|---------|---------|
| 配送问题 | 配送超时、骑手联系不上、配送地址错误、催单 | 38% |
| 订单问题 | 取消订单、修改订单、查看订单状态、重复下单 | 25% |
| 退款/售后 | 申请退款、退款进度、食品质量问题、少送/错送 | 22% |
| 优惠/会员 | 优惠券使用、会员权益、红包问题 | 10% |
| 其他 | 投诉、建议、闲聊、非业务咨询 | 5% |

（酒旅和到店业务线有独立的意图分类体系，共计3套一级意图15个、二级意图87个）

3.1.2 意图识别技术需求

- 模型输入：用户当前消息 + 最近5轮对话上下文 + 用户当前订单状态
- 模型输出：Top3意图（含置信度分数）
- 准确率要求：Top1准确率 ≥ 85%，Top3召回率 ≥ 95%
- 响应时间：P99 ≤ 200ms
- 置信度阈值：≥ 0.7 走自动解决，0.4-0.7 走半自动（推荐方案+人工确认），< 0.4 转人工
- 需支持意图纠偏：用户否定系统判断时（"不是这个问题"），模型基于反馈重新分类

3.1.3 冷启动与新意图发现

- 新业务线接入冷启动：利用已有业务线的预训练模型，通过少量标注数据（约500条）微调
- 新意图发现：对"其他"类别的高频query做聚类分析，月度输出新意图候选列表
- 新意图上线流程：聚类发现 → PM确认 → 标注数据（≥200条）→ 模型更新 → 灰度验证

3.2 槽位填充模块

3.2.1 关键槽位定义

| 槽位名称 | 数据类型 | 是否必填 | 获取方式 |
|---------|---------|---------|---------|
| 订单号 | String | 是 | 自动提取（从用户消息或最近订单）|
| 问题类型 | Enum | 是 | 意图识别输出 |
| 时间信息 | DateTime | 否 | NER提取 |
| 金额信息 | Number | 否 | NER提取 |
| 联系方式 | String | 否 | 用户主动提供 |

3.2.2 槽位填充规则

- 优先级：用户明确提供 > 上下文推断 > 系统自动获取（如最近订单）
- 多订单歧义：如用户有多个进行中订单，需主动追问确认
- 槽位继承：同一会话中已填充的槽位信息在后续轮次中保持，除非用户明确修改

3.3 多轮对话管理

3.3.1 对话状态机

定义了5种对话状态和状态转移规则：

| 状态 | 描述 | 转移条件 |
|------|------|---------|
| INIT | 初始状态 | 用户发送首条消息 |
| UNDERSTANDING | 意图识别中 | 意图置信度<0.7 |
| SLOT_FILLING | 槽位收集中 | 意图确认但缺必要信息 |
| SOLVING | 方案执行中 | 所有必要信息齐全 |
| CLOSED | 会话结束 | 用户确认解决或超时 |

3.3.2 对话策略

- 最大对话轮数：10轮（超过后建议转人工）
- 超时规则：用户5分钟无响应→发送提醒；10分钟无响应→自动关闭
- 上下文窗口：保留最近10轮对话，超出部分做摘要压缩
- 话题切换识别：同一会话中用户切换话题时，自动保存当前上下文并开启新对话流

3.4 人工兜底机制

3.4.1 转人工触发条件

| 条件 | 优先级 |
|------|-------|
| 用户主动要求"转人工" | 最高——立即转接 |
| 意图识别连续2次置信度<0.4 | 高 |
| 同一问题用户连续否定3次 | 高 |
| 涉及敏感操作（大额退款、账号安全） | 高——直接转接 |
| 对话轮数超过10轮未解决 | 中 |
| 用户情绪识别为"愤怒"或"不满" | 中 |

3.4.2 转接体验优化

- 人工客服接手时，自动推送对话摘要（意图、已确认信息、处理进度）
- 用户无需重复描述问题
- 转接过程中展示预估等待时间

五、技术方案（与算法团队共同设计）

  ↓

  ↓（置信度<阈值）

```

成为企业知识管理的AI基础设施——让企业内部的每一份文档、每一条经验都可以被精准检索和智能利用。

1.2 战略定位

- 公司核心产品线之一（占公司整体ARR的45%）
- 目标市场：中大型企业（500人以上），重点行业：金融、法律、制造
- 竞品定位：对标Glean（海外）、XX（国内），差异化在垂直行业的深度定制能力

2.2 核心场景拆解

场景A：新员工入职培训
- 用户故事：作为一名新入职的客服人员，我希望通过问答系统快速了解公司的产品信息、退换货政策和常见问题处理流程，这样我能更快上手工作
- 接受标准：
  * 问答准确率 ≥ 85%
  * 答案必须引用原文出处
  * 支持追问（"那如果是质量问题呢？"）
  * 答案中不能出现与公司政策矛盾的内容

场景B：合规与风控查询（金融行业）
- 用户故事：作为合规部门的分析师，我需要快速查询最新的监管政策和公司合规制度，确保业务操作符合规定
- 接受标准：
  * 答案必须标注引用文档的版本和发布日期
  * 当多个文档存在冲突时，自动标注并按时间排序
  * 不能自行"推理"或"创造"合规建议，只能引用原文
  * 支持审计日志，记录每次查询和返回结果

场景C：技术文档检索（制造行业）
- 用户故事：作为设备维修工程师，我需要在现场快速找到设备维修手册中的特定操作步骤
- 接受标准：
  * 支持图文混合检索（手册包含大量图片和表格）
  * 支持精确到章节段落级别的引用
  * 移动端适配（现场使用手机/平板查询）

三、功能需求

3.1 知识管理模块

3.1.1 文档导入

| 格式 | 支持版本 | 解析精度 | 备注 |
|------|---------|---------|------|
| PDF | 全版本 | 文字提取准确率≥98%，表格识别≥90% | 支持扫描件OCR |
| Word (.docx) | Office 2007+ | 格式完整保留 | 支持批注和修订模式 |
| Excel (.xlsx) | Office 2007+ | 表格结构完整还原 | 支持多Sheet |
| PPT (.pptx) | Office 2007+ | 文字+备注提取 | 图片中文字走OCR |
| Markdown | 通用 | 100% | 支持Mermaid图解析 |
| HTML | 通用 | 正文提取（去噪） | 支持网页URL直接导入 |
| 图片 | JPG/PNG/TIFF | OCR文字提取 | 支持手写体识别（限中英文） |

批量导入：支持文件夹拖拽上传，单次最多500个文件，单文件最大100MB

3.1.2 文档处理Pipeline

```
原始文档
  ↓ [格式解析]
结构化文本（保留标题层级、表格、列表）
  ↓ [智能切分]
语义段落（Chunk）
  ↓ [向量化]
Embedding向量
  ↓ [索引构建]
向量数据库 + 倒排索引（混合检索）
  ↓ [质量校验]
自动化QA验证（抽样10个问题验证检索准确性）
```

3.1.3 智能切分策略

| 策略 | 适用场景 | 参数 |
|------|---------|------|
| 语义切分 | 一般文档 | 目标chunk 500-1000 token，句子完整性保证 |
| 段落切分 | 结构化文档（手册、规范） | 按标题层级切分，保留父标题 |
| 表格切分 | 含大量表格的文档 | 表格独立成chunk，附加表头上下文 |
| 滑动窗口 | 长文本无结构 | 窗口800 token，重叠200 token |

切分后的每个chunk附加元数据：
```json
{
  "chunk_id": "doc001_chunk_023",
  "doc_id": "doc001",
  "doc_title": "2025年信贷业务合规手册",
  "section_path": "第三章 > 3.2 贷后管理 > 3.2.1 风险预警",
  "chunk_text": "...",
  "token_count": 680,
  "page_number": 45,
  "has_table": false,
  "has_image": true,
  "created_at": "2025-08-01T10:30:00Z"
}
```

3.2 检索与问答模块

3.2.1 检索架构

采用多路召回 + 重排序的两阶段检索架构：

第一阶段——多路召回（Recall）：
| 召回路 | 方法 | 候选数 | 说明 |
|--------|------|--------|------|
| 向量召回 | Embedding cosine similarity | Top 50 | 语义匹配 |
| 关键词召回 | BM25 | Top 30 | 精确匹配、专有名词 |
| 知识图谱召回 | 图遍历 | Top 10 | 实体关联（二期） |

第二阶段——重排序（Reranking）：
- 模型：Cross-Encoder（基于BERT-large微调）
- 输入：query + 候选chunk
- 输出：relevance score（0-1）
- 取Top 5进入生成阶段

3.2.2 答案生成

```
检索到的Top5 chunks
  ↓ [Prompt组装]
System Prompt（角色设定+行业约束+引用规则）
+ Context（Top5 chunks，按相关性降序）
+ User Query
  ↓ [LLM推理]
生成答案
  ↓ [Guardrails后处理]
幻觉检测 + 引用验证 + 敏感信息过滤
  ↓ [格式化]
最终答案（含引用标注）
```

3.2.3 Guardrails机制

| 检查项 | 方法 | 触发后处理 |
|--------|------|-----------|
| 幻觉检测 | 答案中每个事实性声明与source chunks做NLI验证 | 标注低置信度片段，或回退为"无法确认" |
| 引用验证 | 每个引用标注与原文做精确匹配 | 引用不匹配则移除该引用并标注 |
| 敏感信息 | 正则+分类模型（身份证号、手机号、银行卡号） | 脱敏或拒绝回答 |
| 合规红线 | 预定义红线词典+分类器 | 拒绝回答+记录日志 |
| 跨文档冲突 | 多source间矛盾检测 | 列出所有版本并标注时间 |

3.2.4 问答质量指标

| 指标 | 定义 | 目标 | 当前值 |
|------|------|------|--------|
| 问答准确率 | 人工评估，答案正确且完整 | ≥ 85% | 89% |
| 幻觉率 | 答案中包含源文档未提及的信息 | ≤ 5% | 3.2% |
| 引用准确率 | 引用标注与原文匹配 | ≥ 95% | 96.5% |
| 无答案识别率 | 知识库确实没有时正确回答"不知道" | ≥ 90% | 87% |
| 平均响应时间 | 从提问到答案展示 | ≤ 3秒 | 2.1秒 |
| 用户满意度 | 点赞/(点赞+点踩) | ≥ 75% | 78% |

三、关键决策与反思

3.1 技术方案选择：Fine-tune + RAG 混合架构

最初方案A（纯RAG）：
- 优点：开发快、成本低
- 问题：金融术语和行文风格不够专业，生成的研报像"AI味很重的科普文章"

最终方案B（Fine-tune + RAG）：
- 用客户提供的500篇历史研报做Fine-tune，让模型学习券商研报的行文风格和专业表达
- RAG负责实时数据注入（行情、财务数据、政策信息）
- 效果：生成文本的"专业度"评分（客户5人评审团打分）从方案A的3.2分提升到4.5分（5分满分）

反思：
- Fine-tune的数据质量比数量更重要。最初用了800篇研报训练，效果反而不如精选300篇高质量研报
- 应该更早做POC验证。最初对纯RAG方案过于乐观，浪费了约3周时间

3.2 数据安全方案的博弈

客户（券商安全部门）的要求：
- 所有数据不出内网
- 不使用任何外部API
- 模型完全私有化部署

我们的应对：
- 在客户机房部署了自研的7B微调模型（2张A100）
- 效果比直接调通义千问API差约15%，但满足了安全要求
- 为弥补模型能力差距，增强了RAG的检索精度和Prompt工程

反思：
- 金融行业客户的安全合规需求要提前评估，直接影响技术路线
- 私有化部署的运维成本远高于预期（部署+调试用了4周，比预期多2周）
- 建议后续项目在售前阶段就拉算法和运维参与技术评估

3.3 需求管理——客户需求的持续膨胀

原始需求（合同范围）：
1. 行业研报初稿自动生成
2. 金融数据自动引用和核验
3. 合规审查

项目中途客户新增的需求（scope creep）：
4. 研报模板管理系统
5. 多分析师协同编辑
6. 研报摘要自动翻译（中→英）
7. 与Wind/Bloomberg数据直连

处理方式：
- 需求4（模板管理）：与核心功能强相关，纳入一期（增加2周工期）
- 需求5（协同编辑）：体验优化类需求，推到二期
- 需求6（翻译）：独立功能，推到二期
- 需求7（数据直连）：涉及第三方对接，需另外评估成本，推到二期并单独报价

反思：
- 定制项目的需求边界必须在合同中明确，否则客户会不断追加
- 每个新增需求都应该走正式的变更流程（我们做到了，但过程中客户有些不满）
- 关键策略：将客户的新增需求转化为二期合同的内容，既不拒绝客户也保护利润

- 文档不够及时：项目中期的技术方案变更没有及时更新PRD和TDD，导致后续接手的测试同学理解不到位

五、经验总结

1. 定制项目的核心挑战不是技术，而是需求管理和客户预期管理
2. Fine-tune数据质量 > 数量，精选数据可以用更少的数据达到更好的效果
3. 金融行业的安全合规需求必须前置评估，直接影响技术路线和项目成本
4. 大客户项目的利润保护：将新增需求转化为二期合同，而不是无限妥协
5. AI项目的效果评估框架需要在立项时就与客户对齐，避免交付时对"好不好"标准不一
