# Phase 4: 入库 + 准备度评估

## 目标

将 Phase 3 生成的全量内容入库为完整项目档案，自动提取索引信息供下游 skill 使用，并通过两层评估判断项目"面试准备度"。

---

## Step 1: 组装完整档案

将 Phase 3 的 6 个阶段内容 + Phase 2 的骨架，按 `schemas/project-card.md` 组装为完整项目档案：

```yaml
project_card:
  metadata:
    project_id: proj-{NNN}
    skeleton_ref: interview-vault/projects/proj-{NNN}/skeleton.md
    created_at: [当前日期]
    last_modified: [当前日期]
    readiness_score: [待计算]
    readiness_details: [待生成]

  stages:
    stage_1_initiation: [Phase 3 阶段1内容]
    stage_2_requirements: [Phase 3 阶段2内容]
    stage_3_data: [Phase 3 阶段3内容]
    stage_4_design: [Phase 3 阶段4内容]
    stage_5_testing: [Phase 3 阶段5内容]
    stage_6_deployment: [Phase 3 阶段6内容]

  extracted_indices: [Step 2 生成]
```

## Step 2: 自动提取索引

从完整档案中自动提取以下信息：

### 技能标签

```
遍历每个阶段的方案本体和技术栈：
  提及但未深入描述 → proficiency: 能用
  在方案本体中有具体运作描述 → proficiency: 懂原理
  在演进脉络中有取舍讨论 → proficiency: 能讲取舍
```

### 量化指标

```
遍历每个阶段的落地参数和骨架中的预期成果：
  提取 metric_name + value + source_stage
  去重，保留最终值
```

### 能力证据

```
遍历方案本体和演进脉络：
  识别能力标签（技术选型、跨部门协调、项目推动、数据治理等）
  关联具体的证据内容
  
按 cross-cutting-probing.md 第四节，确保每个项目至少提取 2 条非技术高价值贡献
  （需求判断力/跨部门推动/资源争取/风险兜底/方法论沉淀）
```

### 追问题库

```
汇集所有阶段的追问预埋：
  按 type（方案/决策/落地/反思）分类
  按 probing_intensity 排序
  ⚠️ 继承 skeleton.md「信源分界」的档位：🔴 零字全推演的内容若进入 qa-bank，
     必须在条目上打标 source: fabricated —— 否则下游 interview-qa 会把它
     当成"必须背下来"的事实，用户照背照讲，面试时出事
```

### 关键词

```
全文提取关键词：
  技术栈关键词
  行业关键词
  方法论关键词
  工具/平台关键词
```

## Step 4: 准备度评估（两层）

### 第一层：结构完备性（自动检查）

| 检查项 | 标准 | 权重 |
|--------|------|------|
| 6 阶段覆盖 | 每阶段有方案本体（最终方案 + 交付物） | 15% |
| 量化指标 | ≥3 个量化成果（含业务指标 + AI 指标），通过行业常识校验 | 15% |
| 追问预埋 | 极高追问阶段每个 ≥4 组，高追问 ≥3 组，中追问 ≥2 组；跨阶段必埋问题已覆盖（见 `cross-cutting-probing.md`：≥2 条"重来会改" + 可迁移分析视角） | 20% |
| 落地参数 | 数据准备和测试验证阶段有具体的人天/耗时/轮次/数量 | 10% |
| 演进脉络 | ≥2 个阶段有完整的演进故事（V1→问题→V2） | 15% |
| 角色一致性 | 全阶段叙事视角与年限匹配，无矛盾 | 10% |
| 数字咬合 | 落地参数之间无矛盾，可交叉验证 | 5% |
| **信源完备** | 有「信源分界」段；骨架级风险已标出且已进入核对清单首位；若 `source_strength` 为"仅口述/无任何依据"，该风险已单独向用户提示 | 10% |
| — | 合计 | **100%** |

**评分规则**：
- 每项检查通过 = 满分
- 部分通过 = 按完成比例折算
- 未通过 = 0 分
- 总分 = 各项加权求和（0-100）

> 结构完备（自洽）与信源完备（真实）是两件事：**档案可以 100% 自洽却 0% 真实**。
> 所以「信源完备」单列一项，且**不受其他项高分补偿** —— 骨架级风险未澄清时，
> 无论总分多少，都应在准备度输出中附一条独立警示。

### 第二层：叙事自检（系统自追问）

系统扮演面试官，对自己生成的全量档案做 3-5 轮追问测试：

**追问测试流程**：

```
for 追问 in 随机选取的 3-5 个追问预埋:
  提取追问预埋中的 question
  用档案中的内容尝试回答
  检查：
    1. 答案是否自洽？（前后不矛盾）
    2. 答案是否够具体？（不模糊带过）
    3. 能否继续追问 2 层？（追问→再追问→再追问，都有内容可答）
  
  if 发现漏洞:
    标记为待补充
```

**追问测试覆盖**：
- 至少覆盖"极高追问"的 2 个阶段（立项、方案设计）
- 至少包含 1 个跨阶段追问（如"方案设计阶段的选型依据和 PoC 阶段的效果是否一致？"）
- 至少包含 1 个"反思类"追问

### 准备度输出

**综合准备度的计算公式**（本次起固定，便于跨项目比较与重算）：

```
综合准备度 = 0.7 × 结构完备性得分 + 0.3 × (叙事自检通过率 × 100)，四舍五入
```

> 两层分开报：**结构完备性**是内部自洽度，**叙事自检通过率**是抗追问度。
> **事实风险不进入这个公式** —— 见 Step 4 末尾的独立警示规则。

```
准备度评估：[项目名]
─────────────────────────────────────────

结构完备性：88/100
  ✅ 6阶段覆盖：完整
  ✅ 量化指标：4个（业务2+AI 2），校验通过
  ✅ 追问预埋：极高阶段各4组，高阶段各3组，中阶段各2组
  ⚠️ 落地参数：数据准备阶段缺标注人天参数 → -7分
  ✅ 演进脉络：方案设计+测试验证阶段有完整迭代故事
  ✅ 角色一致性：全阶段一致
  ⚠️ 数字咬合：标注数量与周期的日产能未明确 → -5分

叙事自检：3/5 轮通过
  ✅ 追问1："为什么选RAG不选fine-tune？" → 答案引用了数据量约束，自洽
  ✅ 追问2："上线后效果怎样？" → 答案有具体数据，可继续追问
  ⚠️ 追问3："数据标注花了多久？" → 答案缺人天参数，追问到第2层中断
  ✅ 追问4："架构怎么设计的？" → 答案完整，可追问3层
  ⚠️ 追问5："如果重新做会怎么改？" → 答案偏泛，需更具体的改进点

综合准备度：85%
  主要缺口：
    1. 数据准备阶段的标注人天参数需补充
    2. 反思类追问的回答需更具体
  
  建议：补充以上2项后可达90%+，面试准备充分
─────────────────────────────────────────
```

**独立警示（强制）**：若「信源完备」检查项未满分，或骨架级风险（🔴 零字全推演）尚未澄清，
必须在准备度输出的末尾附一条**不参与打分**的警示，格式：

```
  独立警示（不受总分补偿）：
    🔴 <骨架级风险的具体内容 + 一旦被追问/背调会怎么崩>
```

## Step 6: 入库存储

准备度评估完成后（无论是否达到满分），将完整档案存入 vault：

```
interview-vault/projects/proj-{NNN}/
├── skeleton.md      # Phase 2 已存
├── full-card.md     # 完整档案（本步骤存入，含 extracted_indices）
└── qa-bank.md       # 追问QA库（从 extracted_indices.qa_bank 导出）
```

### qa-bank.md 的导出方式（别手抄）

`qa-bank.md` **不要手写** —— 它必须与 `full-card.md` 里的 `extracted_indices.qa_bank` 逐字一致，
手抄必然漂移。用随 skill 提供的脚本导出：

```bash
# 必须在 vault 的 projects/ 目录下执行（脚本按 proj-*/full-card.md 相对路径读取）
cd <vault>/projects
python3 <skill>/scripts/export-qa-bank.py            # 不带参数：自动扫描所有 proj-*/full-card.md
python3 <skill>/scripts/export-qa-bank.py proj-004   # 或指定项目
```

脚本行为：
- 从 `full-card.md` 的**最后一个 ```yaml 代码块**解析 `extracted_indices.qa_bank`
- 按阶段分组输出（带追问强度星级），并在文末附「按追问类型速览」
- 自动统计并前置提示 `source: fabricated` 条目数
- **会重写同名 `qa-bank.md`**，但**会保留**已有的「高频通用追问」手工段（检测 `## 高频通用追问`
  起始位置后原样接在末尾）—— 所以脚本可以安全重跑，不用先备份再拼接
- 首次导出时手工段还不存在，仍需按下面的说明补一次；之后重跑就会自动带上

> ⚠️ 导出的 `qa-bank.md` 只有各阶段预埋问答。按 `interview-qa/references/qa-bank-rules.md`
> 的「高频追问补充」，**每个项目**还需手工补一节 **高频通用追问**（最大挑战 / 最大贡献 /
> 量化成果 / 团队协作 / 重新做会怎么改）—— 这 5 条要引用该项目的演进脉络与 metrics，无法脚本化。
> 补写时注意各项目的**讲法边界**，例如 `proj-003` 是个人工具、价值**不得折算成金额**。

### readiness_score 回填

评估完成后，把结果写回 `full-card.md` 顶部的 `metadata` 块：

```yaml
  readiness_score: 91
  readiness_details: "结构完备性 96/100（信源完备 6/10）｜ 叙事自检 4/5 ｜ 综合 91 ｜ ⚠️ 事实风险：🔴 高 —— <一句话原因>"
```

`readiness_details` 必须**同时包含事实风险那一句** —— 否则下游只看到 91 分，
会误以为"这档案很稳"，而事实风险恰恰不体现在分数里。

## 面试复盘的回流机制

面试后如果使用了 interview-review skill 进行复盘，可能产生档案补丁：

1. 补丁存储在 `interview-vault/interviews/<公司-日期>/patches/`
2. 系统提示用户逐条确认补丁内容
3. 用户确认后合并回 `full-card.md`
4. 合并后 `last_modified` 更新
5. `readiness_score` 重新计算
